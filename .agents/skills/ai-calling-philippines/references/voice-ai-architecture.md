# 音声 AI パイプラインのアーキテクチャ

AI 通話システムの内部構造、2 つの方式、レイテンシ設計、会話制御（割り込み・ターンテイキング）の指針。フィリピン国内対応に必要な観点を含む。

## 通話 1 本を構成する 6 つの要素

```
[一般電話/PSTN] ─ [電話網接続] ─ [メディア転送] ─ [音声 AI コア] ─ [観測/記録]
                                                       │
                                  ┌────────────────────┴────────────────────┐
                                  STT → LLM(+ツール) → TTS  /  音声対話モデル
```

1. **電話網接続（テレフォニー）**：一般電話と繋ぐ。電話番号・SIP・CPaaS（`telephony-philippines.md`）
2. **メディア転送**：音声ストリームの運搬。PSTN 側は G.711 μ-law **8kHz 狭帯域**、WebRTC 側は広帯域
3. **STT（音声認識）**：相手の発話をテキスト化
4. **LLM**：応答を生成。予約・CRM 照会などの**ツール（関数呼び出し）**を使う
5. **TTS（音声合成）**：応答テキストを音声化
6. **観測/記録**：録音・文字起こし・レイテンシ・通話結果（`implementation-and-ops.md`）

3〜5（音声 AI コア）の作り方が「方式」の違いである。

## 方式 A：カスケード型（パイプライン）

`STT → LLM → TTS` を直列に繋ぐ。各部品を独立に選定・差し替えできる。

```
発話 ─→ VAD/エンドポインティング ─→ STT(ストリーミング) ─→ LLM ─→ TTS ─→ 応答音声
```

**長所**

- 部品を自由に選べる（STT は Deepgram、LLM は Bedrock の Claude、TTS は ElevenLabs 等）
- テキスト LLM は音声トークンより**安い**。プロンプトキャッシュも効く
- **文字起こしが処理の正本**として確実に残る（記録・分析・eval に有利）
- LLM の出力テキストを検証・整形してから TTS に渡せる（発話内容を制御しやすい）
- **言語混在（タグリッシュ）対応の STT を選びやすい** — 部品差し替えで言語要件に合わせられる

**短所**

- レイテンシが各段で積み上がる
- 相手の声のトーン・感情・間が STT 段で捨てられ、応答が平板になりがち
- 割り込み（barge-in）を自前で制御する必要がある

**向く案件**：発話内容を厳密に管理したい、特定の LLM を使いたい、コストを抑えたい、言語要件（フィリピン英語/タグリッシュ）に合わせて STT を選びたい。

## 方式 B：音声対話型（Speech-to-Speech / Realtime）

単一のマルチモーダルモデルが音声を直接入力し音声を直接出力する。STT/TTS の段を持たない。

**代表的なモデル/API（2026 年時点）**

- **OpenAI Realtime API**（`gpt-realtime` 系）：WebSocket/WebRTC。音声トークン課金
- **Google Gemini Live API**：マルチモーダルのライブ対話
- **Amazon Nova Sonic**（Amazon Bedrock）：音声対音声モデル。野口さん Tier B（AWS）に直結できる

**長所**

- レイテンシが低い（段が少ない）
- 割り込み・相づち・間など会話のリズムをモデルがネイティブに扱う
- 声のトーン・感情・非言語の手がかりを保てる

**短所**

- モデルの選択肢が少なく、フィリピン英語の訛り・タグリッシュ・セブアノ語など低リソース言語への強さはモデル依存（要評価）
- 発話を一字一句制御しにくい
- 音声トークン課金がテキストより高い（`cost-and-accuracy-ph.md`）
- 文字起こしは副産物。記録・eval 用に別途取得する設計が要る
- ツール（関数呼び出し）の成熟度はモデル依存

**向く案件**：会話の自然さ・低レイテンシが最優先、英語中心の対話、AWS 完結（Nova Sonic）。

## 方式選定の指針

| 判断軸 | カスケード型 | 音声対話型 |
|--------|------------|-----------|
| 会話の自然さ・低レイテンシ最優先 | △ | ◎ |
| 発話内容を厳密に制御したい | ◎ | △ |
| 言語（フィリピン英語/タガログ語/ビサヤ語/タグリッシュ）に STT を合わせたい | ◎ | モデル次第 |
| コストを抑えたい | ◎ | △ |
| 文字起こしを正本にしたい | ◎ | △（別取得） |
| AWS 内でデータを完結したい | Bedrock LLM 構成で可 | ◎（Nova Sonic） |

ADR には選定理由とともに「将来もう一方式に切り替える余地」を書く。マネージドプラットフォーム（`service-landscape.md`）は両方式を設定で切り替えられることが多い。

## レイテンシ予算（最重要の設計値）

会話が自然に感じる**応答レイテンシの目標はおおむね 800ms 以下、理想は約 500ms**。「相手が話し終えてから AI の音声が鳴り始めるまで」を指す。

| 区間 | 内容 | 目安 |
|------|------|------|
| エンドポインティング | 相手が話し終えたと判定する無音待ち | 設定次第（最大の調整点） |
| STT 確定 | ストリーミング認識の最終確定 | 数十〜数百 ms |
| LLM TTFT | 最初のトークンが出るまで | モデル/プロンプト次第 |
| TTS 初音声 | 最初の音声チャンクが出るまで | TTS 次第（低遅延 TTS で短縮） |

音声対話型はこの内訳を 1 モデルに畳み込むので有利。カスケード型では**ストリーミング**（STT の途中結果で LLM を先行起動、LLM のトークンを文単位で TTS に流す）でレイテンシを縮める。

### エンドポインティング（無音しきい値）

「相手が話し終えた」と判定する無音時間。**短すぎると話の途中で割り込み、長すぎると沈黙が長く感じる**。固定しきい値だけでなく、**セマンティックターン検出**（小さなモデルで「文として完結したか」を判定。LiveKit のターン検出モデルや各プラットフォームの Smart Endpointing 相当）を併用すると、考えながら話す相手にも自然に応答できる。

## 会話制御（ターンテイキング）

- **VAD（音声区間検出）**：相手が話しているかを検出。雑音環境で誤検出しやすい
- **割り込み（barge-in）**：AI の発話中に相手が話し出したら、**TTS 再生を即停止し、生成中の LLM 出力もキャンセル**して相手の発話を聞く。これが無いと会話が成立しない
- **相づち（backchannel）**：相手の長い発話中に短い相づちを返すと自然。過剰だと邪魔
- **つなぎ発話（filler）**：ツール呼び出し等でレイテンシが伸びる時、つなぎの一言で間を埋める
- **沈黙対応**：相手が無言の時の再プロンプトと、一定時間で終話する設計

## 8kHz 狭帯域という制約

一般電話（PSTN）の音声は G.711（μ-law/A-law）**8kHz 狭帯域**。WebRTC アプリ内通話の 16kHz 以上の広帯域より情報量が少なく、**STT 精度が落ちる**。フィリピン英語の訛り、タグリッシュ、セブアノ語など低リソース言語と重なると劣化が顕著になる。対策：

- STT は**電話音声向けのモデル/設定**（telephony モデル）を選ぶ
- 音声対話型モデルも電話品質の音声で評価してから採用する
- 精度の詳細は `cost-and-accuracy-ph.md`

## ツール（関数呼び出し）

LLM が会話の途中で外部処理を呼ぶ：空き枠照会・予約確定・顧客情報照会・ナレッジ検索（RAG）・人間エージェントへのエスカレーション判定。設計上の注意：

- ツール 1 回はレイテンシを足す → つなぎ発話で吸収する
- ツールの失敗（タイムアウト・エラー）時の発話を必ず用意する
- 予約確定など**副作用のあるツールは冪等に**し、二重実行を防ぐ
- 実装の詳細は `implementation-and-ops.md`

- [ ] 応答レイテンシ目標（800ms 以下）を設定し計測している
- [ ] エンドポインティング（無音しきい値）を案件に合わせ調整、必要ならセマンティックターン検出を併用
- [ ] 割り込み（barge-in）で TTS 停止 + LLM キャンセルが効く
- [ ] つなぎ発話・沈黙対応・終話条件を設計
- [ ] 8kHz 電話音声 + 対象言語（フィリピン英語/タガログ語/ビサヤ語/タグリッシュ）の実データで STT/モデルを評価済み
- [ ] ツールの失敗時発話と副作用ツールの冪等化を設計
