# サービス選定（フィリピン向け AI 通話）

「どのサービスを使うか」の全体像。マネージドプラットフォーム / 自作フレームワーク / 各部品（STT・TTS・LLM・音声対話）の選択肢と、野口さんスタックへの当てはめ方。

> 価格・対応言語・機能は変化が速い。本ファイルの数値・対応状況は**設計時に必ず一次情報で再確認**する。

## 大分類：マネージド vs 自作

### マネージドプラットフォーム（音声ループを任せる）

電話・STT・TTS・割り込み制御・ダッシュボードまで込みのプラットフォーム。**自分で常駐サーバを持たなくてよい**ので 1 名運用・最速出荷に向く。

| プラットフォーム | 特徴 | 課金の形 |
|----------------|------|---------|
| **Vapi** | STT/LLM/TTS/電話を自分で選んで組む柔軟型。プラットフォーム手数料 + 各部品の実費 | プラットフォーム約 $0.05/分 + 部品実費（合計 約 $0.13〜0.31/分） |
| **Retell AI** | STT/LLM/TTS/電話を束ねた単価。設定がシンプル | 約 $0.07/分〜（従量、基本サブスク不要） |
| **Bland AI** | 構成が固定的で割り切った作り | 分課金 |
| **ElevenLabs Agents** | TTS の品質が強み。会話エージェント機能 | 分課金 |

**長所**：最速で出荷、電話まわりを意識しなくてよい、ダッシュボード/録音/文字起こし付属。
**短所**：分課金に上乗せ手数料、データ所在のコントロールが弱い、ベンダーロックイン、細かい挙動を制御しにくい。**フィリピンは人手のエージェントが安いため、手数料が乗るマネージドは ROI を圧迫しやすい**（`cost-and-accuracy-ph.md`）。

### 自作フレームワーク（常駐コンテナで音声ループを持つ）

| 選択肢 | 特徴 |
|--------|------|
| **LiveKit Agents** | OSS の音声エージェントフレームワーク。LiveKit Cloud が WebRTC + SIP テレフォニーを提供。STT/LLM/TTS プラグイン、または音声対話モデルを差せる。ターン検出モデルを持つ |
| **Pipecat**（Daily） | OSS の音声エージェントフレームワーク（Python）。Daily の transport、または Twilio 等のテレフォニーと組む |
| **Twilio ConversationRelay** | Twilio が STT/TTS と電話を担当し、利用者は LLM だけを WebSocket で持ち込む中間形態 |
| **Twilio Media Streams** | 生の音声を WebSocket で受け、STT/LLM/TTS をすべて自前で組む最も低レイヤな構成 |

**長所**：データ所在を制御できる、Bedrock と密結合できる、規模が出ればコスト有利（手数料が無い）、挙動を完全制御、**STT を言語要件（フィリピン英語/タグリッシュ）に合わせて選べる**。
**短所**：常駐インフラ（ECS Fargate 等）の構築・運用、割り込み制御や監視も自前。

> **基本方針**：PoC・最速出荷はマネージド。通話量が多い（手数料が重い）/ データ所在を制御したい / Bedrock を使いたい / STT を細かく選びたい なら自作。ADR に切り替え基準（例「月 X 万分を超えたら自作へ」）を書く。

## 各部品の選択肢（カスケード型を組む場合）

### STT（音声認識）— フィリピン言語の観点が最重要

| サービス | 英語 | タガログ語 | ビサヤ語（セブアノ） | 備考 |
|---------|------|-----------|---------------------|------|
| **Deepgram**（Nova 系） | 強い | 限定的 | ほぼ非対応 | 低レイテンシ・電話音声向けモデルあり。フィリピン英語の訛りは実データ評価が必須 |
| **Google Cloud Speech-to-Text** | 強い | fil-PH 対応 | Chirp 系ユニバーサルモデルでの可否を要確認 | 多言語ユニバーサルモデルは対応言語が広い。言語コードで指定 |
| **Azure AI Speech** | 強い | 対応を要確認 | 対応を要確認 | カスタム音声モデル・発音辞書 |
| **OpenAI**（gpt-4o-transcribe / Whisper） | 強い | 多言語対応 | Whisper は ceb を含むが低精度 | タグリッシュ/ビスリッシュ（混在）の扱いは要評価 |

- **タグリッシュ / ビスリッシュ（コードスイッチング）**は多くの STT が苦手。文中で英語↔タガログ／英語↔セブアノが切り替わると認識が崩れる
- **ビサヤ語（セブアノ語）**は地方言語で話者人口が最大だが、主要 STT/TTS の一級対応が乏しい。ビサヤ諸島・ミンダナオ対象なら対応方針（フル対応/英語誘導/人間転送）を要件決定にする
- ヒリガイノン語・ワライ語・イロカノ語等の対応はさらに乏しい。対象地域を要件定義で確認
- いずれも電話品質の実音声で評価する。詳細は `cost-and-accuracy-ph.md`

### TTS（音声合成）

| サービス | 備考 |
|---------|------|
| **ElevenLabs** | 多言語。英語の品質が高い。フィリピン英語向けの声・フィリピン語の品質は要評価 |
| **Google / Azure ニューラル TTS** | フィリピン語（fil-PH）の音声を持つ。安定 |
| **Amazon Polly**（ニューラル） | AWS 完結。野口さん Tier B と相性良 |
| **Cartesia** 等 | 超低レイテンシ志向。品質は要評価 |

- **セブアノ語（ビサヤ語）の TTS 音声は主要プロバイダで乏しい**。タガログ語 TTS での代用は別言語のため不可。セブアノ語対応が要件なら実音声で評価し、無ければ英語へ寄せる（`cost-and-accuracy-ph.md`）

### LLM

GPT 系 / **Claude（Anthropic API または Amazon Bedrock）** / Gemini。英語・タグリッシュの理解は主要 LLM とも実用域だが、システムプロンプトで応答言語（英語/タガログ語/ビサヤ語）を明示的に固定する。セブアノ語はテキストなら LLM の扱いが比較的良いため、STT/TTS が弱くても通話後の補正・要約には活用余地がある。**Bedrock の Claude**なら野口さん Tier B（AWS）でデータを完結できる。

### 音声対話モデル（方式 B）

- **OpenAI Realtime API**（`gpt-realtime` 系）
- **Google Gemini Live API**
- **Amazon Nova Sonic**（Bedrock）— AWS 内で音声対音声が完結

いずれもフィリピン英語の訛り・タグリッシュへの強さはモデル依存。**採用前に電話品質の実音声で必ず評価**する。

## 野口さんスタックへの当てはめ

### Tier A 経路：マネージド + Next.js 管理 UI（最速出荷）

```
[一般電話] ─ Twilio ─ [Vapi / Retell（音声ループ）] ─Webhook→ [Next.js Route Handler on Vercel]
                                                                      │
                                                              [Supabase: 通話記録/文字起こし/録音メタ]
[Next.js 管理 UI] ─REST→ プラットフォーム API（エージェント設定・架電トリガ）
```

- 音声のリアルタイム処理は**プラットフォーム側**。Vercel には触れさせない（Vercel は長時間接続を保持できない）
- Vercel の Next.js は「管理 UI」「架電のトリガ」「Webhook 受信」だけを担う
- 録音/文字起こしは Supabase（Storage + テーブル）に保存。RLS でマルチテナント分離

### Tier B 経路：自作 + ECS Fargate + Bedrock

```
[一般電話] ─ Twilio SIP / Amazon Connect ─ [LiveKit Agents or Pipecat（ECS Fargate 常駐）]
                                                       │
                                          Amazon Nova Sonic（音声対話）/ Bedrock Claude（カスケード）
                                                       │
                                          [Supabase or RDS: 通話記録/文字起こし]
```

- 音声ループは **ECS Fargate の常駐コンテナ**（野口さん Tier B のスタックにそのまま乗る）
- 手数料が無いぶん、フィリピンの安い人件費と競うコスト設計に向く
- **Amazon Connect** はフィリピンを含むコンタクトセンター運用に使え、通話基盤を AWS 内に寄せられる（リージョン・番号の可否は `telephony-philippines.md` 参照）

### Vercel/Supabase を使ってよい範囲（重要）

| 用途 | 置き場所 |
|------|---------|
| 音声のリアルタイムループ（WebSocket/WebRTC 保持） | **マネージド or ECS Fargate**（Vercel/Edge 不可） |
| 管理 UI、エージェント設定、架電トリガ | Next.js on Vercel |
| Webhook 受信（通話開始/終了・文字起こし完了） | Next.js Route Handler（短時間処理）|
| 通話記録・文字起こし・録音・構造化アウトカム | Supabase（DB + Storage、RLS） |
| 通話後の文字起こし要約・抽出（非同期） | Supabase Edge Function / バッチ |

## 選定の流れ

1. **方式**を決める（`voice-ai-architecture.md`：カスケード型 / 音声対話型）
2. **構築方式**を決める（マネージド / 自作）
3. **PSTN プロバイダ**を決める（`telephony-philippines.md`）
4. **対象言語と STT/TTS** を決める（`cost-and-accuracy-ph.md`）
5. **コスト試算**する（人件費との比較を含む。`cost-and-accuracy-ph.md`）
6. ADR（`docs/11-tech-stack/adr/`）に 1〜5 と切り替え基準を記録

## レビュー観点

- [ ] マネージド / 自作を選び、ADR に切り替え基準を記録
- [ ] 音声ループが Vercel/Supabase Edge に載っていない
- [ ] 対象地域と対象言語（英語/タガログ語/ビサヤ語/タグリッシュ）に合う STT/TTS を選定し、電話品質の実音声で評価
- [ ] 価格・対応言語を一次情報で再確認した
- [ ] 録音/文字起こしの保存先（Supabase 等）と分離（RLS）を決めた
