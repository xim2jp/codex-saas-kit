# Security Compliance Skill

セキュリティを「やっています」ではなく**「この公的基準のこの項目に、この実装で対応しています」と説明できる状態**にするための参照集。認証取得（ISMS/Pマーク）そのものが目的ではなく、**基準を設計の物差しとして使い、顧客説明のアカウンタビリティを確保する**ことが目的。

## 参照する公的基準（物差しとして使う）

| 基準 | 発行元 | 本フレームワークでの使い方 |
|------|--------|--------------------------|
| **中小企業の情報セキュリティ対策ガイドライン** | IPA | 1名運用の組織的対策のベースライン。**SECURITY ACTION（一つ星→二つ星）の自己宣言**は無料で対外説明の第一歩になる |
| **安全なウェブサイトの作り方** | IPA | 実装セキュリティの国内標準チェックリスト。security-auditor の OWASP 監査と併記して国内顧客に説明しやすくする |
| **ISMS / ISO/IEC 27001（附属書A 管理策）** | ISO/JIPDEC | 認証取得はしない前提でも、**管理策との対応表**を作ると ISMS 取得企業（顧客）の委託先評価に回答できる |
| **プライバシーマーク（JIS Q 15001）** | JIPDEC | 個人情報の取得・利用・委託・開示請求のプロセス要求。legal-docs-generator のプライバシーポリシー・外部送信規律と整合させる |
| **NIST CSF 2.0** | NIST | 特定→防御→検知→対応→復旧の枠組み。observability（検知）・release-log/ロールバック（復旧）の説明に使う |
| **OWASP Top 10 / ASVS** | OWASP | 既に security-auditor の監査基準。チェックシートでは IPA 基準と相互参照する |

**使い方の原則**：基準の全項目準拠を目指さない（1名運用で不可能かつ過剰）。**「対応済み／代替策で対応／対象外（理由）」の3値で対応表を埋める**ことがアカウンタビリティの実体。空欄と「検討中」を残さない。

## 脆弱性データベース（監視ソース）

| ソース | 用途 | 監視方法 |
|--------|------|---------|
| **JVN / JVN iPedia** | 国内向け脆弱性情報（日本語）。顧客報告に引用しやすい | 採用スタックのベンダーを MyJVN で絞って週次確認 |
| **NVD（CVE）** | 脆弱性の一次情報・CVSS スコア | 依存関係は npm audit / Dependabot が CVE と自動照合（cicd-pipeline の週次ジョブ） |
| **CISA KEV** | **実際に悪用が確認された**脆弱性カタログ | KEV 掲載＝優先度最上位。該当したら即時ホットフィックス（軽量サイクル外の即応） |
| **GitHub Security Advisory** | npm 等エコシステム固有の勧告 | Dependabot alerts を有効化（リポジトリ設定で必須） |
| **JPCERT/CC 注意喚起** | 国内の攻撃動向・緊急注意喚起 | 週次確認（RSS）。該当技術があれば ops-review に記載 |

**運用ルール**：CVSS だけで判断しない（KEV 掲載・攻撃コード公開・外部公開面かどうかで実効優先度を決める）。対応記録は bug-escape-ledger.md と同様に「検知日・判断・対応・完了日」を残す（顧客説明の証跡になる）。

## EOL（サポート終了）データベース

| ソース | 用途 |
|--------|------|
| **endoflife.date** | Node.js / Next.js / PostgreSQL / Ubuntu 等 300+ 製品の EOL 日付を一元確認。API があり機械監視可能 |
| 各ベンダーのライフサイクルページ | Supabase の Postgres バージョン、Vercel の Node ランタイム、Stripe API バージョン等はベンダー告知が正 |

**運用ルール**：
1. **Phase 7（技術選定）**：採用するランタイム・フレームワーク・DB の EOL 日を ADR に記録（EOL まで2年未満のメジャーバージョンを新規採用しない）
2. **Phase 20（運用）**：operations-analyst が ops-review で「EOL 接近一覧」（12ヶ月以内に EOL を迎える依存）を確認し、更新を改善バックログに起票
3. EOL 超過の依存を本番で使い続けることは**セキュリティパッチ供給停止**を意味する——チェックシートの説明が崩れるため、EOL 前更新を軽量サイクルの定常業務とする

## 成果物：顧客向けセキュリティチェックシート

`docs/50-legal/security-compliance-sheet.md`（legal-docs-generator が雛形生成、security-auditor が監査結果で裏付け）：

```markdown
# セキュリティ対策状況（○○ SaaS）

- 最終更新: YYYY-MM-DD ／ 根拠: security-audit-YYYYMMDD.md（Phase 18 監査）

## 1. 準拠フレームワーク
- IPA「安全なウェブサイトの作り方」: 対応表 §3 ／ SECURITY ACTION: ★★ 自己宣言済み
- ISO/IEC 27001 附属書A: 対応表 §4（対応済み N 項目／代替策 M 項目／対象外 K 項目・理由付き）

## 2. 技術的対策の要点
（認証・アクセス制御=RLS／暗号化／脆弱性管理=週次スキャン＋KEV即応／バックアップ=RPO・RTO は NFR 表と同値）

## 3. 脆弱性・EOL 管理プロセス
（監視ソース・頻度・対応 SLA。直近の対応実績件数）

## 4. 対応表（基準×実装）
| 基準項目 | 対応状況 | 実装・運用の根拠 |
```

- **NFR（non-functional-requirements.md）の数値と必ず一致させる**（チェックシートと要件定義で言うことが違うのが最悪）
- 監査で未達の項目を「対応済み」と書かない（虚偽説明は契約リスク。「対応予定（時期）」と書く）
- 認証（ISMS/Pマーク）を「取得している」と誤認させる表現をしない（参照・準拠と取得は別。取得を求められたら要件として別途見積る）

## SDLC への組み込み

| フェーズ | 作業 |
|---------|------|
| Phase 5 | NFR セキュリティカテゴリで準拠目標（IPA 対応表＋SECURITY ACTION 等）を確定。顧客が ISMS 取得企業なら委託先チェックシートへの回答が必要になる前提で決める |
| Phase 7 | 採用技術の EOL 日を ADR に記録 |
| Phase 18 並列 | security-auditor が監査結果を基準対応表にマッピング |
| 公開前 | legal-docs-generator がチェックシートを生成（プライバシーポリシー等と整合確認） |
| Phase 20 | EOL 接近・脆弱性対応実績を ops-review に記載、チェックシートを最新化 |

## アンチパターン

- 「セキュリティは万全です」とだけ書く（根拠のない安全宣言。基準項目との対応表が説明責任の実体）
- 認証未取得なのに「ISMS 準拠」を「認証取得」と読める表現で書く（優良誤認）
- 脆弱性対応を CVSS 点数だけで機械的に優先順位付け（KEV・公開面・悪用容易性で補正する）
- EOL を迎えた依存の放置（パッチ供給停止＝チェックシート §3 が虚偽化する）
- チェックシートを一度作って放置（Phase 20 で ops-review と同じ周期で更新。日付のない対外文書は信頼を毀損）
