# Concept Playbook（企画の作り方）

Phase 1（企画）で concept-planner が従う手順と問いバンク。Phase 2 で concept-reviewer が判定基準として使う。

## 0. 企画フェーズの目的

「このリポジトリで何を作り、何を成し遂げるのか」を、要件定義に入る前に**一枚の企画書（`docs/01-concept/concept.md`）**に確定する。要件定義は「どう作るかの前の、何を満たすか」を決めるが、企画はさらに前の「なぜ作るか・誰のためか・成功とは何か・どこまでやるか」を決める。

企画が無いまま要件定義に入ると、要件の優先順位の根拠が RFP の記述順になり、ビジネスとして成立しない機能が MUST になる。企画はこれを防ぐ。

## 1. 持ち込み資料の取り込み（最初に行う）

`docs/00-inputs/` を Glob し、存在する資料を**すべて Read** する：

| 資料 | 既定の置き場所 | 取り込み方 |
|------|---------------|-----------|
| RFP（要件定義策定依頼書） | `docs/00-inputs/rfp.md`（他形式はそのまま置いてよい） | 背景・目的・対象業務・制約を企画の一次情報として採用。**機能要件の列挙はまだ扱わない**（Phase 5 の入力） |
| 既存の企画書・事業計画書 | `docs/00-inputs/existing-concept.md` | concept.md の各節へマッピングして転記。不足節だけを対話で埋める。**ゼロから聞き直さない** |
| 参考資料（競合資料・議事録・調査メモ） | `docs/00-inputs/materials/` | 企画の根拠として引用（ファイル名で参照） |

取り込み結果は `docs/00-inputs/INDEX.md`（`templates/inputs-index.md`）に記録する：資料名、取り込み先の節、採用／参考／未使用（理由）。**`docs/00-inputs/` の資料本体は書き換えない**（ユーザーの入力は原本のまま残す）。

資料が何も無い場合は INDEX.md に「持ち込み資料なし」と記録し、対話だけで企画を作る。

## 2. 対話の作法

requirements-architect と同じ規律で進める：

- **1 ターン最大 3 問**。モバイルから答えられる量
- **曖昧語を通さない**（「いい感じ」「DX」「AI 活用」「効率化」は具体化を求める）
- **仮定は明示**（「X と仮定しています」）。毎ターン末尾に仮定リストと未確認項目を更新
- **5 問ごとに復唱**
- **技術選定・画面・機能の詳細に入らない**。「どう作るか」はすべて後続フェーズ。ユーザーが実装の話を始めたら「企画確定後に Phase 5 以降で扱います」と返す
- 合計 10〜12 問で終える。requirements-architect（20 問前後）より軽い。深掘りは要件定義に委ねる

## 3. 問いバンク（取捨選択して使う）

### 3.1 動機と課題仮説（2-3 問）

- なぜ今これを作るのか。きっかけとなった出来事は何か
- 誰が、どの場面で、何に困っているか。その困りごとは**金額・時間・頻度**でどのくらいか
- 困りごとを放置すると半年後に何が起きるか
- 既存の解決手段（競合製品・Excel・人手・放置）で足りない理由は何か

### 3.2 ターゲットと提供価値（2-3 問）

- 最初の顧客を 1 人（1 社）具体的に描くと誰か。実名で当てがあるか
- その人がこのプロダクトを使い続ける理由を一文で言うと何か
- 払う人と使う人は同じか。決裁権はどこにあるか
- 自社プロダクトか、クライアント案件か。クライアント案件なら、クライアント自身の事業上の狙いは何か

### 3.3 達成目標とスコープ（2-3 問）

- このリポジトリで**何を納品・公開したら「成し遂げた」と言えるか**（例：Web アプリ本体＋営業サイト＋ LINE 通知。モバイルアプリは対象外）
- 3 ヶ月後・6 ヶ月後にどの数値がどうなっていれば成功か（有料顧客数、MRR、利用頻度、業務時間削減）
- **やらないこと**を 3 つ挙げると何か
- 将来やるかもしれないが今回は入れないものは何か

### 3.4 制約と前提（2 問）

- 期限とその根拠（補助金・イベント・契約・希望）
- 予算と支払い条件。1 名で運用し続けられる負荷か
- 法規制・業界規制・個人情報の取り扱いで、今の時点で分かっているものは何か

### 3.5 撤退条件（1 問）

- 何が起きたら（何が起きなかったら）やめるか。やめるときユーザーとデータをどうするか

## 4. 「リポジトリ成果物スコープ」の定義（企画書の必須節）

本フレームワークは 1 リポジトリ = 1 案件で、アプリ本体だけでなく営業ポータル・法務文書・運用手順書・MCP サーバー・モバイルアプリまで成果物になりうる。企画書で**このリポジトリが最終的に何を含むか**を列挙し、含まないものを明示する：

| 成果物候補 | 含める／含めない | 理由 |
|-----------|----------------|------|
| Web アプリ本体 | | |
| 営業ポータル（LP 兼営業サイト） | | 「含めない」の場合、Phase 9 の営業ポータルモック必須ルールのスキップ根拠になる（要件定義書にも転記する） |
| 管理画面 | | |
| モバイルアプリ（iOS / Android） | | |
| LINE 連携（LIFF / Messaging API） | | |
| AI エージェント向け MCP サーバー | | |
| 法務文書（利用規約・プライバシーポリシー・特商法） | | 一般公開する SaaS なら原則含める |
| 多言語・多通貨 | | |

この表が `docs/99-pm/document-set.md` のプロファイル初期判定（`full-saas` / `internal-tool` / `api-mcp` / `minimal`）の根拠になる。concept-planner は Handoff で PM にプロファイル候補を提案する。

## 5. 達成目標 ID（OBJ-NN）

企画書の達成目標には `OBJ-NN` を発番する（例：OBJ-01（有料顧客 30 社 / 6 ヶ月））。業務要件（BZ）・KPI（KPI-NN）はこの OBJ を上流 ID として持つ。トレーサビリティは **OBJ → BZ → F → S / API / ENT / PS → UC** で貫通する（document-catalog.md 準拠）。

## 6. 企画レビュー（Phase 2）の判定基準

concept-reviewer は以下を確認する。Critical があれば Block：

- 課題仮説が**金額・時間・頻度のいずれかで定量化**されている（「困っている」だけは Major）
- ターゲットが**具体的な 1 人**まで描かれている。払う人と使う人の区別がある
- 提供価値が一文で書かれ、既存手段との差分が説明されている
- **達成目標（OBJ）が定量**で、期限が付いている
- **リポジトリ成果物スコープ表**が埋まり、「含めない」に理由がある
- **やらないこと**が 3 つ以上ある
- 撤退条件が数値で書かれている
- RFP がある場合、企画が RFP の背景・目的と矛盾していない（矛盾があれば OQ として明記されている）
- 1 名運用・財務制約（一括払いのみ）に反する前提が無い
- 技術選定・画面・詳細機能に踏み込んでいない（踏み込んでいれば Minor で指摘し、後続フェーズへ送る）
- 曖昧語が残っていない

## アンチパターン

- RFP の機能一覧をそのまま企画書に写す（企画は「なぜ・誰に・何を成し遂げるか」。機能は Phase 5）
- ユーザーが既に企画書を持っているのにゼロから質問を始める（取り込みが先）
- 成功指標を「売れたら」「使われたら」で済ませる
- 「含めない」成果物を書かず、後で営業ポータルや法務文書が「無いことに気付く」
- 企画フェーズで技術スタックやアーキテクチャを決めてしまう（Phase 7 の tech-stack-architect の領域）
- 企画書が 10 ページを超える（1 枚で読める。詳細は戦略と要件定義に委ねる）
