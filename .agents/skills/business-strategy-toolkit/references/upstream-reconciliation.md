# Upstream Reconciliation（企画×戦略×RFP の突合ルール）

Phase 5（要件定義）の冒頭で requirements-architect が行う、**3 つの上流入力の統合手順**。Phase 6 で requirements-reviewer が整合性の判定基準として使う。project-manager は矛盾の差し戻し判定に使う。

## 1. 3 つの入力と役割

| 入力 | 正本 | 役割 | 要件定義での扱い |
|------|------|------|-----------------|
| 企画書 | `docs/01-concept/concept.md`（Phase 2 Approve 済） | なぜ・誰に・何を成し遂げるか。達成目標 OBJ。リポジトリ成果物スコープ | **スコープと優先順位の根拠**。企画に無い成果物は要件に入れない |
| ビジネス・マーケティング戦略書 | `docs/02-business-strategy/business-strategy.md`（Phase 4 Approve 済） | 市場・ポジショニング・収益モデル・チャネル・KPI・営業ポータル要否 | **ビジネスモデル節・成功指標節・非機能要件（規模）の根拠**。チャネル・課金方式が機能要件を生む（例：従量課金 → メータリング機能） |
| RFP（要件定義策定依頼書） | `docs/00-inputs/rfp.md`（ユーザー配置。無い案件もある） | 発注者・ユーザーが求める機能・制約・期限の一次情報 | **機能要件・制約の一次情報**。ただし企画・戦略で採用されなかった機能は OQ に落とす |

## 2. 突合表の作成（`docs/03-requirements/upstream-reconciliation.md`）

requirements-architect はヒアリングを始める前に、`templates/upstream-reconciliation.md` で突合表を作る：

1. 企画書の OBJ・成果物スコープ、戦略書の収益モデル・チャネル・KPI・営業ポータル要否、RFP の要求項目を**1 行 1 項目**で列挙
2. 各項目について 3 入力の記載有無と内容を並べ、判定を付ける：
   - **一致**：3 入力（または記載のある入力同士）が同じ方向 → 要件に採用
   - **補完**：片方にしか無いが矛盾しない → 要件に採用（出所を明記）
   - **矛盾**：方向が違う → §3 の優先順位ルールで仮決めし、**必ず OQ-NNN を起票**してユーザー判断を仰ぐ
   - **上流欠落**：RFP にあるが企画・戦略に無い機能・成果物 → 要件には**入れず** OQ に落とす（企画の成果物スコープ外の可能性）
3. 突合表を完成させてから対話を始める。対話の質問はまず**矛盾と上流欠落の解消**に使う

## 3. 矛盾時の優先順位ルール

| 矛盾の種類 | 優先する入力 | 理由 | 仮決め後の処置 |
|-----------|-------------|------|---------------|
| 何を作るか（成果物スコープ） | 企画書 | 企画は Phase 2 でレビュー済みの合意 | RFP 側の追加要求は OQ。ユーザーが採用を決めたら **Phase 1 へ差し戻し**て企画書を改訂（軽微なら差分追記） |
| なぜ・誰に（ターゲット・提供価値） | 企画書 → 戦略書 | 戦略は企画のターゲットを前提に組まれている | RFP のターゲット記述と違えば OQ |
| どう売るか・いくらか（収益・チャネル） | 戦略書 | Phase 4 で数値の整合をレビュー済み | RFP の価格・販路記述と違えば OQ。ユーザーが RFP を優先するなら **Phase 3 へ差し戻し** |
| 具体的な機能・業務の詳細 | RFP | 発注者の一次情報。企画・戦略は機能詳細を扱わない | 企画のスコープ内であれば採用 |
| 制約（期限・予算・法規制） | RFP → 戦略書 | 発注者側の確定事項が多い | 戦略の時間軸と違えば OQ |
| 非機能（規模・可用性） | 戦略書（SOM・KPI） → RFP | 想定規模は戦略の SOM から | NFR の数値根拠として戦略書を引用 |

**勝手に解釈して片方を黙って捨てることは禁止**。矛盾は必ず OQ になり、decision-log に判断を残す。

## 4. 差し戻し判定（PM）

requirements-architect が Handoff で「上流差し戻し候補」を挙げたら、PM は次で判定する：

- 企画書の**達成目標・成果物スコープ・ターゲット**が変わる → Phase 1 へ戻す（concept-planner 修正モード → concept-reviewer）。戦略も影響するなら続けて Phase 3
- 戦略書の**収益モデル・チャネル・KPI 目標・営業ポータル要否**が変わる → Phase 3 へ戻す（business-strategist 修正モード → business-strategy-reviewer）
- 企画・戦略の**表現の補足で済む**（数値や文言の追記） → 差し戻さず、requirements-architect が decision-log に記録し、該当文書に差分追記（Handoff に明記）
- RFP 側の記述が古い・誤りと判明 → `docs/00-inputs/` は書き換えず、INDEX.md に「RFP §X は OQ-NNN で上書き」と記録

差し戻しは rework-loop.md のループカウントとは別枠（上流フェーズの新規ループとして数える）。

## 5. 要件レビュー（Phase 6）での確認項目

requirements-reviewer は以下を確認する：

- `upstream-reconciliation.md` が存在する（無ければ Critical。RFP が無い案件でも企画×戦略の 2 入力で作る）
- 「矛盾」「上流欠落」の全行に OQ-NNN が付いている（付いていなければ Critical）
- 要件定義書の MUST 機能がすべて企画の成果物スコープ内にある（スコープ外の MUST は Critical）
- ビジネスモデル節・成功指標節が戦略書の収益モデル・KPI と一致している（不一致は Major）
- 営業ポータル要否が戦略書 §5 と一致して要件定義書に明記されている
- 非機能要件の規模（想定ユーザー数）が戦略書の SOM・ローンチ計画と桁で合っている

## 6. RFP が無い案件

自社プロダクトなど RFP が無い場合、突合は企画×戦略の 2 入力で行う。RFP 列は「なし」と書く。requirements-architect のヒアリングは企画・戦略で決まっていない**機能の詳細**に集中する（なぜ・誰に・どう売るかを聞き直さない）。

## 7. 既存案件（v0.16.0 より前に要件定義済み）への適用

既に `requirements.md` がある案件に Phase 1-4 を後付けする場合：

- concept-planner は既存の requirements.md §1〜2・§6〜7 を「既存企画書」として取り込み、concept.md を**要約として**作る（requirements.md は書き換えない）
- business-strategist も同様に requirements.md §6（ビジネスモデル）を起点に戦略書を作る
- 突合表は作るが、既存要件との矛盾は「次サイクルの Phase 5 で解消」として OQ に残すだけでよい（既存文書の分割・改名はしない。document-catalog.md §7 の追記型ルール）

## アンチパターン

- 突合表を作らずヒアリングを始める（RFP の記述順が優先順位になる）
- 矛盾を requirements-architect が独断で解決して OQ を起票しない
- RFP の全機能を MUST に入れる（企画の成果物スコープを見ていない）
- 企画・戦略を要件定義の中で「書き直す」（差し戻すべきものを下流で吸収する）
- `docs/00-inputs/` の RFP を編集して整合させる（原本は残す）
