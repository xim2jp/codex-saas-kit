# Review Protocol（全レビュワー共通）

全レビュワーエージェント（requirements-reviewer、planning-reviewer、external-design-reviewer、ui-mockup-reviewer、agent-experience-reviewer、internal-design-reviewer、test-plan-reviewer、implementation-reviewer、security-auditor）が共有するレビュープロトコル。

> **必読**：レビュー後の手戻り・再レビューの進め方は `references/rework-loop.md`（修正ループプロトコル）が正本。Block を出したら必ずループが回る前提でレポートを書くこと。

## Self-Check の確認（v0.13.0、L0 プロトコル）

レビュー対象の成果物には producer の **Self-Check ブロック**（提出前セルフレビュー結果。`lifecycle-loop.md` 準拠）が添付されているはずである：

- **Self-Check が無い成果物は即差し戻してよい**（Verdict を出す前に PM 経由で producer に差し戻し。ループカウントは消費しない）
- Self-Check で fail のまま提出された項目は、理由の妥当性を最初に確認する
- Self-Check が全項目 pass なのに同種の指摘が複数出る場合、**producer のチェックリスト形骸化**として指摘に含める（L0 の Check 機能の修理。PROJECT_LEARNINGS への記録候補）
- レビュワーの役割は Self-Check で拾える浅い抜け漏れの再発見ではなく、**独立した視点による深い指摘**に集中する

## レビュースタンス

### 1. Pedantic but Honest

細かい指摘も漏らさず、しかし**捏造はしない**。指摘するならエビデンスを示す。「気になる」「もしかしたら」レベルは Minor/Nit に降格、根拠が出せないものは**書かない**。

> **A clean review is a valid review.** 指摘ゼロも正当な結果。レビューを正当化するために指摘を作らない（manufacture しない）。

### 2. Severity Inflation の禁止

**Severity inflation（重要度の膨らませ）は最も深刻な失敗モード**。レビュワー本人の信頼を毀損する。

各指摘について、書く前に4つの質問に答える。1つでも「いいえ」「不明」があれば**重要度を下げるか削除**：

1. ファイル名と行番号（あるいは該当箇所）を正確に引用できるか？
2. 具体的な失敗モード（入力、状態、悪い結果）を説明できるか？
3. 周辺コンテキストを読んだか？（既に上流で処理されている可能性は？）
4. その重要度は弁護できるか？（Minor を Critical と書いていないか？）

### 3. クリーン承認のしきい値

| 指摘の状況 | Verdict |
|----------|---------|
| Critical 0件、Major 0件 | **Approve**（Minor/Nit があっても可） |
| Critical 0件、Major 1件以上 | **Warning**（修正推奨、blocking ではない） |
| Critical 1件以上 | **Block**（修正必須） |

## 重要度分類

### 🔴 Critical（修正必須・blocking）

以下のいずれか：
- 要件を満たせない、または重大な要件違反
- セキュリティ脆弱性、データ漏えい
- データ損失、整合性破壊
- 法規制違反、コンプライアンス違反
- 重大な業務影響（停止、誤動作）
- 上流成果物との明らかな矛盾

### 🟡 Major（修正強く推奨）

以下のいずれか：
- 設計の不整合、論理矛盾
- 性能上の重大な懸念
- 保守性に深刻な影響
- テスト・検証ができない設計
- ベストプラクティスからの大きな逸脱

### 🟢 Minor（記録のみ、blockingしない）

- 命名・文書の不明瞭さ
- 軽微な冗長性
- スタイル・規約の些細な違反
- 改善提案レベル

### ⚪ Nit（参考程度、無視可能）

- 好みの問題
- 代替案の提示
- 将来の検討材料

## レビュー結果フォーマット

レビュー結果は対応するフェーズの `reviews/YYYY-MM-DD-<reviewer-name>-loopN.md` に書き出す（N = ループカウント。初回 = loop1。同日再レビューでも上書きされない）。

```markdown
# レビュー結果: <レビュー対象>

- **レビュワー**: <reviewer-name>
- **レビュー日**: YYYY-MM-DD
- **レビュー対象**:
  - `docs/.../xxx.md`
  - `docs/.../yyy.md`
- **レビュー観点**: pedantic（細部まで確認）
- **ループカウント**: N/5
- **総合Verdict**: 🟢 Approve / 🟡 Warning / 🔴 Block

## サマリー

| 重要度 | 件数 |
|--------|------|
| 🔴 Critical | 0 |
| 🟡 Major | 2 |
| 🟢 Minor | 5 |
| ⚪ Nit | 3 |

**判定理由**: （Approve/Warning/Block にした根拠を1-2行で）

## 🔴 Critical Issues

### C-001: <タイトル>

- **該当箇所**: `docs/.../xxx.md` 第N節、第M行
- **問題**: （具体的に何が問題か）
- **失敗モード**: （どう破綻するか）
- **根拠**: （要件IDや上流文書との対比、または業界標準）
- **修正提案**: （具体的な修正案）
- **担当エージェント**: <修正を依頼する設計エージェント名>

## 🟡 Major Issues

（同形式）

## 🟢 Minor Issues

| ID | 該当箇所 | 問題 | 提案 |
|----|---------|------|------|
| m-001 | `docs/.../xxx.md` L120 | 命名が不明瞭 | `foo` → `customerOrderTotal` |

## ⚪ Nits

- n-001: `docs/.../xxx.md` L200 — 表記揺れ「ユーザ」「ユーザー」

## ✅ Positive Highlights

レビュー対象の良い点も必ず記録する（モチベーション維持・パターン学習のため）：

- ✅ Use Case ベースのAPI設計が一貫している
- ✅ エラーハンドリングが画面ごとに定義されている

## 📋 Action Checklist

修正担当エージェントが対応するアクション一覧：

- [ ] C-001: 該当箇所の修正（担当: external-designer）
- [ ] M-001: 該当箇所の修正（担当: external-designer）

## 🔄 Verdict ブロック（機械可読・必須）

レポート末尾と完了報告メッセージの**両方**に、以下のブロックを必ず含める。project-manager がこれをパースして修正ループを自動起動する（詳細は `rework-loop.md`）：

```
VERDICT: BLOCK | WARNING | APPROVE
LOOP: N/5
RETURN_TO: <修正担当エージェント名>（APPROVE 時は NEXT_PHASE）
REPORT: docs/.../reviews/YYYY-MM-DD-<reviewer-name>-loopN.md
```

修正フローの原則：

```
1. Block → PM が <担当エージェント> を修正モードで自動起動（ユーザー確認不要）
2. 担当エージェントが指摘を反映し、対応表（reviews/...-response-loopN.md）を作成
3. 本レビュワーが再起動され、対応表と成果物を照合
4. 5回目のループでも未解決の場合、project-manager にエスカレーション
```
```

## 再レビュープロトコル

### 起動時のチェック

レビュワーは起動時に以下を確認：

1. `reviews/` 配下に過去のレビュー結果（`*-loopN.md`）があるか
2. ある場合、最大の loop 番号 + 1 を今回のループカウントとする
3. **今回が5回目のレビューで、なお Approve に至らない場合**、レポートと完了報告に以下を明記して PM のエスカレーションを要請：

```
このレビュー対象は修正ループの上限（5回）に到達しました。
project-manager によるエスカレーションが必要です。選択肢：

1. 上流フェーズに戻る（指摘の根本原因が上流にある場合）
2. ユーザーの裁量で approve を強制（Defer 記録付き）
3. スコープ・要件の見直し
```

### 再レビュー時のスコープ制限

2回目以降のレビューは**前回指摘の対応状況を主軸に評価**する：

- **対応表（`reviews/YYYY-MM-DD-<producer>-response-loopN.md`）を必ず照合**。対応表が存在しない、または前回の Critical/Major に対応記載が無ければ即 Block
- 前回 Critical → 解消されているか、成果物の実体で確認（対応表の自己申告を鵜呑みにしない）
- 前回 Major → 解消されているか確認
- 前回 Minor/Nit → 対応の有無を記録（blocking しない）
- **無変更再提出の検出**：成果物に実質的変更が無いのに「修正済」とされていれば `NO-CHANGE` として即 Block
- **新規指摘は最小限に**（同じレベルの観点を新たに発見した場合のみ）

### ユーザーによる Verdict 上書き

ユーザーは以下のいずれかで進行可能：

- 「Approve を強制」: Block/Warning でも次フェーズへ進む（記録は残す）
- 「Defer」: 指摘を後フェーズに先送り（リスクと共に記録）
- 「Reject」: レビュー対象自体を破棄、上流に戻る

## レビュワーが触らないこと

- **設計ファイル本体への書き込み禁止**：レビュワーの Write は **`reviews/` 配下の自分のレポート（`*-loopN.md`）のみ**に許可される。成果物本体・他フェーズのファイルには一切書き込まない
- **修正の代行禁止**：「こう直すべき」と提案するが、自分では直さない
- **責任範囲外の指摘禁止**：例えば外部設計レビュワーがブランド戦略を指摘しない

## 上流成果物との照合

各レビュワーは以下を必ず読んでから評価開始：

- `docs/00-requirements/requirements.md`（全レビュワー必須）
- 自分のフェーズの直前の成果物
- 直前のフェーズのレビュー結果（過去ループの蓄積を反映）

## アンチパターン（レビュワー側）

これらを発見したら自己修正：

- 同じ Issue を異なる視点で2回書く（重複指摘）
- 「考慮すべき」「検討してください」だけで具体性がない
- 「ベストプラクティス的には...」だけで該当案件への適用性を説明しない
- ファイル名・行番号がない指摘
- 既に上流で議論済みの論点を蒸し返す
- レビュー対象に書かれていないことを批判する（書かれていない＝足りないなら Critical/Major で指摘する）

## 執筆ルール・文書セットとの関係（v0.17.0、document-catalog.md が正本）

- **執筆ルール違反は指摘対象**（Minor〜Major）：指示代名詞（「あれ」「それ」「上記の」）による参照、ID 単独の記号参照（名称併記なし）、冒頭「この文書について」節の欠落、用語の glossary 未登録・独自定義。ただし**既存案件の過去文書への遡及適用はしない**（改訂・新規分のみ）
- **document-set.md で「除外」された文書の不存在を指摘しない**：レビュー開始時に `docs/99-pm/document-set.md` があれば確認する。除外文書を前提とした指摘（例：営業ポータルモックが無い）は誤指摘となる
- レビュワーは htmldocs/（生成物）をレビューしない。レビュー対象は常に docs/ の Markdown（正本）
