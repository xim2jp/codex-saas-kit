# AI 通話 Skill（日本国内対応）

人間と AI が**音声通話でリアルタイムに会話する**システムを、**日本国内での利用を前提**に設計・構築するための知識集。受電（インバウンド：問い合わせ一次対応・予約受付・FAQ）と架電（アウトバウンド：リマインド・督促・調査・一次営業）の両方を対象とする。

**「AI 通話」は単一の技術ではなく、音声認識（STT）・大規模言語モデル（LLM）・音声合成（TTS）・電話網（PSTN）接続・リアルタイム制御の合成物**である。この Skill は「どのサービスを使うか」「コストはいくらか」「日本語の精度はどうか」「一般電話とつなげるか」「法令は何を守るか」を一望できるようにする。

> フィリピン国内対応の案件では `ai-calling-philippines` Skill を参照する。言語（英語/タガログ/タグリッシュ）・電話番号制度・法令（DPA 2012 / NTC / SIM 登録法）が日本とは根本的に異なるため、Skill を分けている。

## いつこの Skill を参照するか

- **要件定義**（Phase 1）：「電話を AI で受けたい/かけたい」要望の実現性・方式・コストを見極める時
- **技術スタック選定**（Phase 3）：カスケード型/音声対話型、マネージド/自作、PSTN プロバイダの選定を ADR 化する時
- **外部設計**（Phase 5）：通話フロー（会話シナリオ）、IVR/エスカレーション、画面（管理 UI・通話履歴）設計時
- **内部設計**（Phase 7）：常駐プロセスの置き場所、Webhook、録音/文字起こしの保存、状態管理設計時
- **テスト計画**（Phase 9）：通話品質・精度・レイテンシ・シナリオ網羅のテスト戦略策定時
- **実装**（Phase 11）：音声エージェント・Webhook・通話発信 API を実装する時
- **テスト**（Phase 11-12）：テスト架電、シナリオ評価（eval）、負荷/同時通話数の検証時
- **本番運用**：電話番号取得、開示文言、録音保持、監視ダッシュボード設計時
- **レビュー**（Phase 14）：越境移転・録音開示・エスカレーション経路・コスト上限の確認時

## 重要原則（必読）

### 1. 「AI 通話」を最初に 2 つの方式に切り分ける

| | カスケード型（パイプライン） | 音声対話型（Speech-to-Speech / Realtime） |
|--|---------------------------|------------------------------------------|
| 構成 | STT → LLM → TTS を直列に繋ぐ | 単一のマルチモーダルモデルが音声を直接入出力 |
| 代表 | Deepgram + Claude/GPT + ElevenLabs | OpenAI Realtime（gpt-realtime）、Gemini Live、**Amazon Nova Sonic（Bedrock）** |
| 長所 | 部品を差し替え可、LLM を自由選択、テキスト LLM は安い、文字起こしが正本 | 低レイテンシ、割り込み（barge-in）に強い、声のトーン・間が自然 |
| 短所 | レイテンシが積み上がる、感情・抑揚が落ちる | モデル選択肢が少ない、発話を厳密制御しにくい、音声トークン課金が高め |

> **基本方針**：会話の自然さ・低レイテンシ最優先なら音声対話型。発話内容の厳密な制御・好きな LLM（Bedrock の Claude 等）・安価さ重視ならカスケード型。要件定義で必ず決める。詳細は `references/voice-ai-architecture.md`。

### 2. リアルタイム音声処理は Vercel / Supabase Edge では動かせない

音声エージェントは**通話が続く間ずっと WebSocket/WebRTC 接続を保持する常駐プロセス**を必要とする。Vercel の Serverless Functions・Supabase Edge Functions は短命で長時間接続を保持できないため、**音声ループをそこに載せてはいけない**。選択肢は 2 つ：

- **マネージドプラットフォーム**（Vapi / Retell 等）に音声ループを任せる（野口さん Tier A 向き）
- **常駐コンテナ**（**ECS Fargate** / Fly.io 等）に LiveKit Agents / Pipecat を載せる（野口さん Tier B 向き）

これが AI 通話案件で**最重要のアーキテクチャ判断**。詳細は `references/service-landscape.md`。

### 3. 「マネージド」と「自作」を要件で切り分ける

- **マネージド（Vapi / Retell / Bland / ElevenLabs Agents）**：電話・STT・TTS・割り込み制御まで込み。最速で出荷でき 1 名運用に向く。分課金に上乗せ手数料、データ所在・ベンダーロックインに注意。
- **自作（LiveKit Agents / Pipecat + Twilio / Amazon Connect）**：データ所在を国内に保てる、Bedrock と密結合できる、規模が出ればコスト有利。実装・運用コストは高い。

> **基本方針**：最初の数案件・PoC はマネージド。データ所在要件が厳しい/通話量が多い/Bedrock 必須なら自作。詳細は `references/service-landscape.md`。

### 4. 一般電話（PSTN）接続には日本の電話番号取得が要る

「システムから一般の固定電話・携帯電話と通話する」には、PSTN に繋がる電話番号が必要。日本の番号は種別ごとに取得条件が違う：

- **050（IP 電話番号）**：CPaaS で最も取得しやすい。一部の着信者は 050 を警戒する
- **0AB-J（03/06 等の固定電話番号）**：その市外局番エリアの所在地証明が要る。信頼されやすい
- **0120/0800（フリーダイヤル）**：着信課金。受電業務向け
- **070/080/090（携帯番号）**：原則 CPaaS では発番されない（キャリア/SIM 紐付け）

詳細・取得手続き・発信者番号の考え方は `references/telephony-japan.md`。

### 5. 日本語音声認識は英語より難しい — 重要情報は必ず復唱確認する

日本語は分かち書きがなく、同音異義語・固有名詞（氏名・地名）・数値（電話番号・金額・日時）の誤認識が起きやすい。さらに**電話音声は 8kHz 狭帯域**で、16kHz 広帯域より精度が落ちる。

> **基本方針**：氏名・電話番号・金額・日時・予約内容など**ミスが許されない情報は AI に必ず復唱（復唱確認）させる**。数字入力は DTMF（プッシュ）フォールバックも用意する。固有語はキーワードブースト/カスタム辞書に登録する。詳細は `references/cost-and-accuracy-jp.md`。

### 6. 個人情報の越境移転に注意する

通話音声・文字起こしは**個人情報**。これを米国の STT/LLM/TTS（OpenAI・Deepgram 等）に送る行為は、個人情報保護法上の**外国にある第三者への提供（越境移転）**に該当しうる。利用目的の通知・本人同意または相当措置の確保が要る。データ所在を国内に保ちたい案件では **Amazon Connect 東京リージョン + Bedrock（Nova Sonic / Claude）** の構成が有力。詳細は `references/compliance-japan.md`。

### 7. AI である旨と録音を開示する

- **AI 開示**：相手が「人間ではなく AI と話している」と分かるようにする。法律上の一律義務は未整備だが、消費者の信頼・総務省/経産省の AI 事業者ガイドラインの方向性から、通話冒頭で AI 応対である旨を述べる。
- **録音開示**：録音する場合は冒頭で告知する（例「品質向上のため通話を録音します」）。

詳細は `references/compliance-japan.md`。

### 8. レイテンシ予算を最初に設計する

会話が自然に感じる応答レイテンシは**おおむね 800ms 以下、理想は約 500ms**。内訳は VAD/エンドポインティング（無音判定）・STT・LLM の TTFT・TTS の初音声。**エンドポインティングの無音しきい値**が体感を大きく左右する（短すぎると話の途中で割り込む、長すぎると「沈黙が長い」）。ツール呼び出し（CRM 照会等）はレイテンシを足すので、つなぎ発話（「少々お待ちください」）で吸収する。詳細は `references/voice-ai-architecture.md`。

### 9. 人間へのエスカレーション経路を必ず設計する

AI が「分からない」「STT 信頼度が低い」「相手が苛立っている」「センシティブな話題」を検知したら、**人間へ転送（warm transfer）またはコールバック予約**へ逃がす。エスカレーション無しの AI 通話は重大なクレーム源になる。詳細は `references/implementation-and-ops.md`。

## エージェント別の使い方ガイド

### requirements-architect

- 「電話を AI で」要望に対し、**受電/架電のどちらか**、**会話シナリオの複雑さ**、**月間想定通話分数**、**データ所在要件**、**既存電話番号の有無**を要件として確定する
- 一般電話との接続要否（PSTN か、アプリ内通話のみか）を明確化する（`references/telephony-japan.md`）
- 録音可否・AI 開示・個人情報の取り扱いを要件定義書に明記（`references/compliance-japan.md`）

### tech-stack-architect

- `docs/11-tech-stack/adr/NNNN-ai-calling.md` に記録：
  - **方式選定**：カスケード型 / 音声対話型（原則 1）
  - **構築方式**：マネージド（Vapi/Retell）/ 自作（LiveKit/Pipecat on ECS Fargate）（原則 2・3）
  - **PSTN プロバイダ**：Twilio / Amazon Connect 東京 / その他（`references/telephony-japan.md`）
  - **野口さん適性**：データ所在を国内に保つなら Amazon Connect 東京 + Bedrock（Tier B）。最速出荷なら Vapi/Retell + Next.js 管理 UI（Tier A）
- ADR に「想定通話分数 × 分単価のコスト試算」を必ず添付（`references/cost-and-accuracy-jp.md`）

### external-designer

- **会話フロー（シナリオ）**を画面遷移図と同じ粒度で設計：挨拶 → 本人/用件確認 → 分岐 → 復唱確認 → クロージング → エスカレーション
- 管理 UI の画面一覧：エージェント設定、通話履歴、文字起こし閲覧、録音再生、発信予約、ダッシュボード
- IVR・DTMF フォールバック・営業時間外の扱いを設計

### internal-designer

- 常駐プロセスの置き場所（マネージド / ECS Fargate）を確定（原則 2）
- Webhook（通話開始/終了・文字起こし完了）の受け口と冪等化、録音/文字起こしの Supabase 保存、構造化アウトカム抽出を設計
- 関数呼び出し（予約・CRM 照会・RAG）とレイテンシ吸収を設計（`references/implementation-and-ops.md`）

### test-planner / tester

- テスト架電（人手 + LLM 駆動の模擬発信者）によるシナリオ評価を計画
- 精度（WER・固有語・数値）・レイテンシ・割り込み・同時通話数のテスト観点を網羅（`references/cost-and-accuracy-jp.md`）
- 通話は決定的でないため eval（シナリオ合否・回帰）を中心に据える（`references/implementation-and-ops.md`）

### implementation-worker

- `references/service-landscape.md` の選定に従い実装。音声ループを Vercel/Supabase Edge に載せない（原則 2）
- 重要情報の復唱確認を会話設計に組み込む（原則 5）
- API キー・チャネルシークレットはサーバ専用、フロントに出さない

### implementation-reviewer

- 越境移転対応、録音/AI 開示、エスカレーション経路、コスト上限（最大通話長・無音タイムアウト）、Webhook 署名検証を確認
- `references/compliance-japan.md` のチェックリストを適用

## SaaS 量産戦略への貢献

### 電話という「枯れたが巨大な」チャネルを取り込む

日本の中小企業・地域事業者は今も電話が主要な接点。AI 通話を SaaS に組み込めば、Web/LINE では拾えない層（電話しかしない顧客・営業時間外の取りこぼし）を売上フローに乗せられる。

### 1 ソース化と再利用

通話の会話ロジック（システムプロンプト・ツール・RAG）と、Web/LINE のチャットロジックは**ドメイン知識を共有**できる。Supabase の顧客データ・予約データを通話とチャットの両方から使う 1 ソース構成を取る。将来 `@noguchi/saas-ai-calling` テンプレ化（ROADMAP と整合）。

### 売上直結フローを電話でも保証

- 受電：着信 → 本人/用件確認 → FAQ/予約 → 取りこぼし時はコールバック予約
- 架電：リスト → 発信 → 会話 → アウトカム構造化 → CRM 反映
- これらを eval（Phase 12）でガードする

## アンチパターン（よくある失敗）

1. **音声ループを Vercel/Supabase Edge に載せる**：長時間接続を保持できず通話が切れる。常駐プロセスを使う
2. **方式（カスケード/音声対話）を決めずに着手**：後から作り直しになる。ADR で先に決める
3. **コストを試算せず本番投入**：分課金が積み上がり想定外の請求。最大通話長・無音タイムアウトを設定する
4. **重要情報を復唱確認しない**：誤認識のまま予約・金額が確定しクレームに。必ず復唱する
5. **越境移転を考慮せず米国 STT/LLM に音声送信**：個人情報保護法違反リスク。同意取得か国内構成
6. **AI 開示・録音開示をしない**：信頼を損ね、苦情・規制リスク。冒頭で開示する
7. **エスカレーション経路がない**：AI が詰まると顧客が孤立。人間へ逃がす導線を必ず作る
8. **エンドポインティングを既定のまま放置**：話の途中で割り込む/沈黙が長い。無音しきい値を調整する
9. **8kHz 電話音声を 16kHz 前提のモデルで処理**：精度が落ちる。電話特化モデル/設定を使う
10. **固有名詞をカスタム辞書に入れない**：商品名・地名・人名を誤認識し続ける
11. **AI 通話を緊急通報の代替にする**：CPaaS 番号は 110/119 に繋がらないことが多い。代替にしない
12. **マネージドのまま規模拡大しコストが見合わなくなる**：通話量が増えたら自作への移行を検討する
