# 一般電話（PSTN）接続と日本の電話番号

「システムから一般の固定電話・携帯電話と通話できるか」「日本の電話番号をどう取得するか」の指針。

> 番号取得の可否・必要書類・料金は CPaaS の規約改定や総務省の制度で変わる。**取得着手時に各社の最新情報を必ず確認**する。

## 結論：一般電話とつなげるか

**つなげる。** ただし PSTN（公衆電話網）に接続できる**電話番号と通話基盤（CPaaS / クラウド電話）**が要る。アプリ内の VoIP 通話だけなら電話番号は不要だが、本 Skill が想定する「電話で受ける/かける」は PSTN 接続が前提。

- **受電（インバウンド）**：自社が保有する番号にかかってきた通話を AI が受ける
- **架電（アウトバウンド）**：自社の番号を発信者番号として、相手の固定/携帯にかける

## 日本の電話番号の種別

| 種別 | 例 | CPaaS での取得 | 用途・特徴 |
|------|----|--------------|-----------|
| **050（IP 電話番号）** | 050-XXXX-XXXX | 取得しやすい | 受電/架電に広く使える。一部の着信者は 050 を警戒し出ない傾向 |
| **0AB-J（地理的固定番号）** | 03 / 06 / 052 など | その市外局番エリアの**所在地証明**が要る | 信頼されやすい。発信者番号にすると応答率が上がる |
| **0120 / 0800（フリーダイヤル）** | 0120-XXX-XXX | 取得可（条件あり） | 着信側課金。受電窓口向け |
| **携帯番号（070/080/090）** | — | **原則発番されない** | キャリア/SIM に紐づく。CPaaS では基本扱えない |

> **設計上の含意**：架電業務の応答率を上げたいなら 0AB-J を発信者番号にしたい → エリアの所在地が要る。手早く始めるなら 050。受電窓口なら 0120 も候補。**携帯番号を大量に並べる運用は日本ではできない**前提で設計する。

## PSTN プロバイダ（通話基盤）の選択肢

| プロバイダ | 日本の番号 | 特徴 |
|-----------|-----------|------|
| **Twilio** | 050 / 0AB-J / フリーダイヤル | 世界標準の CPaaS。番号取得に**規制バンドル（本人/所在地確認書類）**が要る。国内サポートあり |
| **Amazon Connect（東京リージョン）** | 日本の番号を提供 | AWS のクラウドコンタクトセンター。**通話基盤・番号・データ所在を AWS 内に保てる**。Bedrock/Lex と統合しやすく野口さん Tier B と好相性 |
| **Vonage / Plivo 等の海外 CPaaS** | 番号により可否が異なる | 日本番号の在庫・規制対応はプロバイダ差が大きい |
| **国産クラウド電話 / CPaaS** | 0AB-J を含め強い | 国内事業者は番号取得・電気通信事業法対応の相談がしやすい |

> **野口さん向けの目安**：データ所在を国内に寄せたい・AWS で完結したい → **Amazon Connect 東京**。マネージドプラットフォーム（Vapi/Retell）に任せる → 多くは **Twilio** を裏で使う。

## 番号取得の実務（Twilio の例）

1. **規制バンドル（Regulatory Bundle）の作成**：日本の番号は本人確認・所在地確認の書類提出が要る。0AB-J はその市外局番エリアの所在地証明が必要
2. 審査の通過を待つ（即時ではない。スケジュールに織り込む）
3. 番号を購入し、Voice の Webhook / SIP / アプリに紐付け
4. 発信者番号として使う番号は**自社が正当に保有する番号のみ**。番号偽装（スプーフィング）はしない

国産 CPaaS / Amazon Connect でも、所在地・本人確認の考え方は同様。**「番号がすぐ手に入る」前提でスケジュールを組まない**。

## SIP トランク / SIP 接続

自作構成（LiveKit Agents / Pipecat）で電話と繋ぐとき、CPaaS が提供する **SIP トランク**経由で音声を常駐コンテナに引き込む。

- LiveKit Cloud は **SIP（インバウンド/アウトバウンド）**をサポートし、PSTN ↔ WebRTC を橋渡しする
- Twilio の **Elastic SIP Trunking** で SIP 経由の発着信を構成できる
- 既存の PBX / クラウド電話を持つ案件では、その SIP トランクに AI 側を相乗りさせる設計もある

## 発信者番号と応答率（架電の設計）

- **発信者番号の表示**：相手に表示される番号。0AB-J（地域番号）は応答率が高い傾向、非通知や見知らぬ 050 は出られにくい
- **発信時刻**：常識的な時間帯に限定する（早朝・深夜の架電はしない）。特定商取引法・苦情対策の観点でも重要（`compliance-japan.md`）
- **再架電**：不在・拒否のリストを管理し、過度な再架電をしない（特定商取引法の再勧誘禁止）

## 受電の設計

- **着信ルーティング**：営業時間内は AI、時間外は留守電/コールバック予約、AI が無理なら人へ転送
- **IVR / DTMF**：「ご予約は 1、お問い合わせは 2」などのプッシュ操作。数字の聞き取りミスを避ける場面で有効
- **同時着信数**：CPaaS/プラットフォームの同時通話上限（チャネル数）を超えると話中になる。想定ピークで見積もる

## 緊急通報の制約（必読）

CPaaS / IP 電話番号は **110・119 などの緊急通報に発信できない**ことが多い。AI 通話システムを緊急連絡の手段として設計・案内してはいけない。要件に緊急性がある案件では、別の連絡手段を併設する。

## 番号ポータビリティ

既存の電話番号を AI 通話システムへ移したい場合、番号ポータビリティ（ポーティング）が使えることがある。番号種別・元事業者により可否と所要期間が異なるため、**早期に確認**する。

## レビュー観点

- [ ] 一般電話接続の要否を確定（PSTN か、アプリ内 VoIP のみか）
- [ ] 使う番号種別（050 / 0AB-J / フリーダイヤル）を決定
- [ ] 番号取得に必要な書類・審査期間をスケジュールに織り込んだ
- [ ] PSTN プロバイダ（Twilio / Amazon Connect 東京 / 国産）を選定
- [ ] 発信者番号が自社の正当な保有番号で、偽装していない
- [ ] 架電の時間帯・再架電ルールを設計
- [ ] 同時通話数（チャネル数）をピーク想定で見積もり
- [ ] 緊急通報の代替にしていない
