## 2. ユースケース記述

1 件ずつ以下の形式で書く。**利用者のアクションとシステムのアクションを分けて**書き、基本・代替・例外の 3 種類のシナリオを必ず考える。シナリオの各行は連番ではなく枝番（1, 1a, 1b）で書く。

### UC-BILLING-01 有料プランを申し込む

- **目的（親 BZ）**：BZ-003（売上データを Stripe から自動取込する）
- **主アクター**：ROLE-01 一般会員　**副アクター**：Stripe（EXT）
- **トリガー**：トライアル残 3 日の通知メール、または料金ページの「申し込む」ボタン
- **事前条件**：ログイン済み。契約状態＝trialing（状態遷移は requirements.md §状態遷移）
- **事後条件**：契約状態＝active。請求が 1 件作成されている。確認メールが送信されている
- **入力**：プラン（月額／年額）、支払い方法　**出力**：契約（ENT 契約）、請求（ENT 請求）
- **扱うエンティティと CRUD**：契約 U／請求 C／会員 R

| # | 利用者のアクション | システムのアクション |
|---|------------------|---------------------|
| 1 | 料金ページでプランを選ぶ | 選択プランの金額（税込）と次回請求日を表示する |
| 2 | 支払い方法を入力して確定する | Stripe Checkout を生成し、決済結果を受け取る |
| 3 | — | 契約状態を active に更新し、確認メールを送る |

**代替シナリオ**

- 1a. 年額を選んだ場合：割引率と一括請求額を表示する（以降 2 へ）
- 2a. 既に支払い方法が登録済みの場合：入力を省略し確認画面へ

**例外シナリオ**

- 2x. 決済が拒否された（ERR 候補：決済失敗）：契約状態は trialing のまま。エラー理由と再試行導線を表示する
- 3x. Webhook が届かない：日次の再取込 JOB で突合し、不一致は運営者に通知する（NFR-OPS-03）

- **業務ルール**（表・式で書く。自然言語の長文にしない）：

| 条件 | 月額 | 年額 |
|------|------|------|
| 請求タイミング | 申込日を起点に毎月同日 | 申込日に一括 |
| 日割り | しない | しない |

- **非機能の注記**：ピーク 50 件/時でも決済完了まで ≦ 10 秒（NFR-PERF-02）
- **理由（なぜこの仕様か）**：戦略書 §4.1 の収益モデル（月額・年額の 2 軸）に従う。日割りをしないのは運用の単純化（決定 D-007）
- **Phase 7 追記欄**：関連 F／業務フロー上の位置／新規 UC の有無

## 3. 例外・特殊処理の抽出チェック（全 UC 横断）

通常処理（業務量の 95% 以上）を書いた後、以下の観点で例外・特殊処理を洗い出した結果を書く。

| 観点 | 確認内容 | 該当 UC / 処理 |
|------|---------|---------------|
| 5W2H | 商品・プランによる違い／相手（ロール）による違い／時期・順序・状態による違い／場所による違い／理由による違い／方式による違い／量・金額による違い | |
| 入力ミス・二重操作 | 二重送信、ブラウザバック、途中離脱 | |
| 期間またぎ | プラン変更の月跨ぎ、年度更新、トライアル終了日、料金改定 | |
| 責任者不在・運営者不在 | 1 名運用で休暇中に起きる処理 | |
| 緊急時・外部障害 | Stripe／メール／AI API 停止時の業務継続（NFR-ENV） | |
| サービス時間外 | 計画停止中の申込・決済 | |
| 特殊処理 | キャンペーン、無料枠超過、返金、解約と再契約、アカウント統合 | |

分岐には発生頻度（滅多に起きないか）を添え、頻度が低く影響も小さい分岐は「人手運用でカバー」と明記して MVP から外してよい。
