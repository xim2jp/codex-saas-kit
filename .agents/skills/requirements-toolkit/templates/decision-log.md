# Decision Log

要件定義の過程で行った判断・確認内容を時系列で記録する。後から「なぜこの仕様になったか」を追跡可能にすることが目的。

各エントリは以下の形式で記録：

```
## YYYY-MM-DD HH:MM - 判断ID: D-XXX

**フェーズ**：（フェーズ番号と名前）

**種別**：仕様判断／要求の採否（採用・先送り・棄却）／変更要求の採否／未決要件の取り扱い／上流差し戻し

**関連 ID**：BZ-… / UC-… / NFR-… / OQ-…（OQ の回答ならここに OQ を書き、open-questions.md の決定列に本 D を書く）

**論点**：
（何について議論したか）

**選択肢**：
- A：...
- B：...
- C：...

**選択**：
（採用した選択肢と理由）

**前提となる仮定**：
（この判断が成り立つ前提条件。崩れたら再検討が必要）

**ユーザー発言（要旨）**：
> 「...」

**影響範囲**：
（この判断が他のどの要件・機能に影響するか）

**未確定の派生論点**：
- ...

**遡って修正した文書**：（変更要求を採用した場合。requirements.md §… / business-requirements.md BZ-… / use-cases.md UC-…）

**ステータス**：仮確定 / 確定 / 要再確認
```

---

## 記録のコツ

1. **議論が分岐した瞬間に書く**：「Aと言っていたけどBに変わった」という変化を残す
2. **却下した選択肢も書く**：なぜ採用しなかったかを残すことで、後の蒸し返しを防ぐ
3. **ユーザーの言葉をそのまま引用する**：要約だけだとニュアンスが失われる
4. **「仮確定」と「確定」を分ける**：当日合意したが、後日上位承認が必要なものは「仮確定」のまま置く
5. **判断者を明記する**：複数のステークホルダーがいる場合、誰の決定かを記録
6. **捨てた要求・先送りした要求も記録する**：採否の経緯が無いと後で蒸し返される。business-requirements.md の採否列と対応させる
7. **決定済み事項の変更は影響と効果を書く**：当事者間で安易に受け入れず、PM・発注者の判定を経たことを残す（requirements-management.md §3）

## 使い方の例

要件定義書ドラフト作成後、各要件IDから対応する判断IDへのリンクを張ると、後のレビューや変更時に追跡しやすい。

例：要件定義書の F-003 → decision-log の D-012, D-015 を参照、など。
