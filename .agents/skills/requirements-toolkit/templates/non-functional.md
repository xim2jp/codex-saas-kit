# 非機能要件一覧（docs/03-requirements/non-functional.md）

> この文書について：非機能要件を **6 カテゴリ × 計測可能な値**で確定し、各項目に検証方法（どのテストで確認するか）を付ける。requirements-architect が Phase 5 で作成、requirements-reviewer が欠落・曖昧語・1 名運用との整合を見る。tech-stack-architect（Tier 判定）、test-planner（non-functional-tests.md）、cost-guardian、observability-integration、Phase 19 kpi-baseline の直接入力。想定読者：発注者・設計者・テスト担当。
> 関連文書：`requirements-toolkit/references/non-functional-requirements.md`（Tier A 既定値と決め方の正本）／要件定義書（requirements.md）／ユースケース一覧（use-cases.md）／外部連携一覧（docs/10-business-design/external-integrations.md）
> ID：`NFR-<CAT>-NN`。CAT ＝ AVL 可用性／PERF 性能・拡張性／OPS 運用・保守性／MIG 移行性／SEC セキュリティ／ENV システム環境・制約

- **作成日**：YYYY-MM-DD　**作成者**：requirements-architect　**版**：v0.1（draft）
- **参照プロファイル**：Tier A 既定値（non-functional-requirements.md §2）。既定値と異なる項目には**差分理由**を必ず書く

## 0. ビジネス領域の要求（メトリクスを決める前に確認する意思）

技術的なメトリクスの前に、発注者・経営側の**意思**を要求として確認する。ここが判断に迷ったときの拠り所になり、優先順位の最上位になる。

| 要求の種類 | 確認項目 | 回答（要求） | 出所 |
|-----------|---------|-------------|------|
| 業務特性／サービス時間 | 提供先（企業内／企業間／コンシューマ）、提供地域（国内／国外）、提供時間（通常・特定日）、繁忙期・閑散期、利用者数、拠点・端末数 | | 戦略書 §3, §5.4 |
| 業務継続 | 停止を許容できない業務の範囲、計画停止の可否、単一障害時／多重障害時の許容 | | |
| 業務連携 | 外部システム連携の有無と方法（Stripe／IdP／LINE／AI API） | | |
| 業務量 | 取扱量（件/月）、1 年後・2 年後の拡張見込み（利用者数 × 倍/年） | | 戦略書 §1.1 SOM, §5.4 |
| 運用方針／内部統制 | 運用範囲・場所、1 名運用の前提、監査証跡の要否 | | concept §7 |
| セキュリティ | 個人情報の有無と種類、順守する法令・ガイドライン、第三者診断の要否、顧客からのセキュリティチェックシート要求の有無 | | 戦略書 §8 |
| ユーザビリティ | 初心者／顧客向けか熟練者向けか、アクセシビリティ要求、対応言語 | | |

「現行と同じでよい」と言われた項目も、現行の値を書き下ろす（Web 化やクラウド化で意図せず悪化することがある）。
