# 非機能要件（NFR）定義ガイド（v0.13.0、v0.17.0 改訂）

要件定義の非機能要件を「性能・可用性・セキュリティ・運用」の一言で済ませず、**計測可能な目標値**として確定させるためのガイド。IPA「非機能要求グレード」の 6 大項目を、1 名運用・Tier A 中心の野口さん SaaS に合わせて軽量化したもの。requirements-architect（決め方と Tier A 既定値）、requirements-reviewer（欠落・曖昧語・一律値のチェック）、test-planner（non-functional-tests.md への変換）、tech-stack-architect（Tier 選定の入力）、cost-guardian、observability-integration が参照する。成果物は `templates/non-functional.md`（`docs/03-requirements/non-functional.md`、NFR-<CAT>-NN）。

> v0.17.0 の改訂点（IPA『ユーザのための要件定義ガイド 第2版』7.12・7.13・事例 26 を反映）：ビジネス領域の要求を先に確認する手順、条件付きメトリクス、レベル値の語彙、検証方法列の必須化、運用要件・移行計画の取り込み、カテゴリコードの確定。

## 原則

1. **全項目に数値・レベル値・列挙、または「対象外（理由）」を入れる**。「高い可用性」「十分な性能」は要件ではない
2. **Tier A 既定値から出発する**。1 名運用 SaaS で過剰な NFR は運用負荷・コストに直結する（野口 Profile：過剰品質の警戒）。既定値と異なる項目には差分理由を書く
3. **一律の値にしない**。「画面応答 2 秒以内」とまとめず、業務・時間帯・ピーク条件で分ける（「1 分間に最大 500 件の入力時に 2 秒以下で応答する確率 95%」のように条件と水準を書く）
4. **ビジネス領域の要求 → メトリクス**の順に決める。技術メトリクスから入ると「早いに越したことはない」でオーバースペックになる
5. **全項目に検証方法**（どのフェーズのどのテスト・監視で確認するか）を付ける。検証できない NFR は書きっぱなしになる
6. NFR は下流の直接入力になる：test-planner の non-functional-tests.md、tech-stack-architect の Tier 判定、cost-guardian の試算、observability の SLO・アラート閾値、runbook の運用スケジュール、Phase 19 kpi-baseline

## カテゴリコード（ID：NFR-<CAT>-NN）

| CAT | カテゴリ | 主な関心 |
|-----|---------|---------|
| AVL | 可用性 | 稼働率、運用時間・計画停止、RTO／RPO／RLO、業務継続の要求度、大規模災害時の再開目標 |
| PERF | 性能・拡張性 | 応答時間（条件付き）、同時接続・業務量・データ量（現在と 1〜2 年後）、Core Web Vitals、スケール方針 |
| OPS | 運用・保守性 | 運用体制、監視、バックアップ、デプロイ、サポート SLA、運用スケジュール、保守容易性（**運用要件書の内容をここに含める**） |
| MIG | 移行性 | 既存データ取込とクレンジング責任、公開方式（スモールスタート）、並行利用と切り戻し、データエクスポート（**全体移行計画の内容をここに含める**） |
| SEC | セキュリティ | 認証・認可、個人情報、通信・保存、監査証跡、脆弱性対応、法令、準拠目標・説明責任、守りきれない場合の検知と手順 |
| ENV | システム環境・制約 | 対応ブラウザ・デバイス、多言語・多通貨、外部依存の障害時方針、月額ランニング上限、アクセシビリティ（ユーザビリティ目標） |

## 決め方（4 ステップ）

1. **ビジネス領域の要求を確認する**（テンプレ §0）：提供先・提供時間・利用者数・業務継続の範囲・業務量と拡張見込み・運用方針・セキュリティ方針・ユーザビリティ。戦略書（SOM・ローンチ計画・SEG）と企画書（制約）から転記できるものは転記する。判断に迷ったときの拠り所はこの領域の要求で、優先順位も最上位
2. **Tier A 既定値を当てる**：下表の既定値を各カテゴリに置き、差分がある項目だけ深掘り質問する。「現行と同じでよい」と言われた項目も現行の値を書く（Web 化・クラウド化で意図せず悪化することがある）
3. **条件・優先度・検証方法を付ける**：条件（対象業務・時間帯・ピーク）、優先度（Must／Should／Could。IPA の Must／Need／Want／Hope に対応）、検証方法（k6・E2E・演習・監視・設定確認）
4. **トレードオフと前提条件を決める**：セキュリティ強化 vs 利便性、稼働率 vs 1 名運用のように矛盾する要求は、ビジネス領域の要求を優先して決着し、前提条件（Vercel/Supabase の SLA に依存 等）はリスクとして管理する。性能は余裕があれば**体感**で合意する（現行 3 秒・目標 1 秒でも 2 秒で十分なことがある）

## Tier A 既定値（6 カテゴリ）

### 1. 可用性（AVL）

| 項目 | Tier A 既定値 |
|------|--------------|
| 稼働率目標（SLO） | 99.5%/月（年間許容停止 ≒ 44 時間。Vercel/Supabase の SLA に依存。1 名運用で 99.9% 超を約束しない） |
| 運用時間・計画メンテナンス | 24 時間提供。計画停止あり（深夜帯、事前告知 ≧ 3 日） |
| RTO（復旧時間目標） | 営業時間内 ≦ 4 時間／夜間は翌営業開始まで |
| RPO（データ損失許容） | ≦ 24 時間（Supabase 日次バックアップ）。課金データは Stripe 側が正・実質 0 |
| 業務継続の要求度 | 単一障害時：ログイン・決済は継続、参照系は停止許容（業務ごとにレベルを分ける） |
| 大規模災害時の再開目標 | ≦ 1 週間（マネージドサービスの復旧に依存） |
| 障害検知 | アラート通知から覚知まで ≦ 30 分（営業時間内） |

稼働率の読み替え（24 時間 365 日）：99%＝87.6 時間/年、99.5%＝43.8 時間/年、99.9%＝8.76 時間/年、99.99%＝52.6 分/年。

### 2. 性能・拡張性（PERF）

| 項目 | Tier A 既定値 |
|------|--------------|
| 応答時間 | 主要画面 p95 ≦ 1.5 秒、API p95 ≦ 500 ms、AI 生成系は非同期＋進捗表示（条件：想定ピーク同時数・データ量を併記） |
| 業務量・同時接続 | MAU・ピーク同時ユーザー数・件/分を明記（k6 の目標値）。稼働当初と 1〜2 年後の 2 時点 |
| データ量 | 1 年後の想定レコード数・ストレージ・保存期間（無料枠超過予測は cost-guardian へ） |
| Core Web Vitals | LCP ≦ 2.5 秒／INP ≦ 200 ms／CLS ≦ 0.1（営業サイト・公開ページは必須） |
| スケール方針 | Vercel/Supabase の自動スケールに委任。上限到達時の Tier B 移行条件を明記 |
| 想定外 | ピーク超過時の挙動（レート制限・キュー・縮退）を 1 行書く |

### 3. 運用・保守性（OPS）

| 項目 | Tier A 既定値 |
|------|--------------|
| 運用体制 | 野口さん 1 名（前提として明記。24 時間対応は約束しない。休暇中は自動復旧＋翌営業日） |
| 監視 | エラー監視（Sentry 等）＋死活監視＋KPI（observability-integration 準拠） |
| データ整合の自己点検 | 外部サービス（Stripe）⇄ DB の日次突合と不一致通知 |
| バックアップ・リストア | Supabase 標準＋リストア手順の文書化（年 1 回リストア演習） |
| デプロイ | CI/CD 経由のみ（cicd-pipeline Skill 準拠）。ロールバック手順必須 |
| サポート窓口・SLA | 問い合わせ応答目標（例：2 営業日以内）。B2B 契約では明文化。AI 一次応答の要否 |
| 運用スケジュール | 月次（請求確定・コスト棚卸し）、年次（証明書・ドメイン更新・リストア演習） |
| 保守容易性 | 文言・設定値のハードコード禁止範囲（稼働後の変更要求に備える） |

### 4. 移行性（MIG）

| 項目 | 確認事項 |
|------|---------|
| 既存データ取込 | 有無・件数・形式・クレンジング責任（顧客）・取込リハーサル要否。5 年に 1 回使う程度のデータは移行しない |
| 公開方式 | スモールスタート（招待制・限定公開 → 一般公開）か一斉公開か。フィーチャーフラグの要否 |
| 並行利用・切り戻し | 旧手段との並行期間・切り戻し条件（決済不整合 ≧ 1 件 等） |
| データエクスポート | 解約時のユーザーデータ持ち出し手段（CSV 等。利用規約と整合） |
| 教育・オンボーディング | 初回利用時の案内（onboarding-designer）。研修データに個人情報を使わない |

### 5. セキュリティ（SEC）

| 項目 | Tier A 既定値 |
|------|--------------|
| 認証・認可 | Supabase Auth＋RLS 全テーブル（security-auditor の監査対象）。管理者・運営者は多要素認証 |
| 個人情報 | 取得項目の最小化（項目を列挙）・保存場所・暗号化・PII のログ/監視ツール混入禁止・保持期間 |
| 通信・保存 | TLS 必須・at-rest はマネージド暗号化に委任 |
| 監査証跡 | 管理者操作・権限変更・決済関連操作のログと保持期間 |
| 脆弱性対応 | npm audit を CI で常時＋Critical は 72 時間以内（軽量サイクル/ホットフィックス） |
| 法令・規制 | 個人情報保護法・外部送信規律（legal-docs-generator と整合）。業界固有規制はここで列挙 |
| 準拠目標・説明責任 | 参照する公的基準（IPA「安全なウェブサイトの作り方」対応表・SECURITY ACTION・ISO27001 附属書 A 対応表等）と、顧客向けセキュリティチェックシートの要否（`security-compliance` Skill、v0.14.0） |
| 守りきれない場合 | 不正アクセスの事実を確認できる仕組み（ログ）、漏えい時の連絡・報告手順（runbook） |

### 6. システム環境・制約（ENV）

| 項目 | 確認事項 |
|------|---------|
| 対応ブラウザ・デバイス | 既定：Chrome/Edge/Safari/Firefox 最新版＋モバイルブラウザ。IE 非対応を明記 |
| 多言語・多通貨 | 対象言語・通貨（i18n-and-currency Skill）。日本語のみなら「対象外」と明記 |
| 外部依存 | 依存 SaaS（Stripe/AI API/メール/LINE）の障害時方針（resilience-testing の演習対象） |
| 予算制約 | 月額ランニングコスト上限（cost-guardian の試算と往復。野口さん財務制約：一括払いのみ） |
| アクセシビリティ・ユーザビリティ | WCAG 2.1 AA の対象項目、初心者向け／熟練者向けの区別、対応言語 |

## フェーズ間の接続（NFR の流れ）

```
Phase 3 戦略書（SOM・ローンチ計画・SEG・法規制）→ §0 ビジネス領域の要求に転記
Phase 5 requirements-architect が non-functional.md を埋める（6 カテゴリ × 条件 × 検証方法）
  → Phase 6 requirements-reviewer：6 カテゴリ網羅＋数値化＋条件付き＋検証方法を検証（曖昧語・一律値は Block）
  → Phase 7 tech-stack-architect：可用性・性能・規制強度から Tier 判定／cost-guardian：PERF の規模と ENV の上限で試算
  → Phase 13 test-planner：non-functional-tests.md に変換（k6 目標値・a11y 対象・障害シナリオ）
  → Phase 19 runbook（OPS・MIG）、kpi-baseline.md（SLO・エラー率の初期目標）
```

## アンチパターン

- 「高速」「安定」「セキュア」のまま確定する（検証不能。requirements-reviewer は曖昧語として Block）
- 1 名運用で 99.99% や 24 時間対応を約束する（守れない SLA は契約リスク。Tier A 既定値から交渉する）
- 一律の値で決める（「全画面 2 秒」。業務・ピーク・時間帯で条件を分ける）
- 「現行と同じ」で済ませる（現行の値を書かないと、機能は同じでも非機能が意図せず悪化する）
- NFR を要件定義で書いたきり、テスト計画・監視設計・runbook に接続しない（検証方法列が空のまま確定しない）
- 全カテゴリを Tier B 相当で盛る（コスト・運用負荷の過剰。既定値との差分には理由を書く）
- 運用・移行を「後で考える」（運用時間・サポート・データ取込・公開方式は基盤設計と費用に効く。Phase 5 で方針を決める）
