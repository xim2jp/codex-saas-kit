# 要件定義マネジメント（v0.17.0）

要件定義を「期間内に、決めるべきことを決めて、終わらせる」ためのマネジメント手順。ステークホルダの特定、要求量の制御、変更の手続き、トレーサビリティ、決まらない要件の扱い、完了判断を扱う。requirements-architect が実施し、PM（project-manager）が完了判断の材料として使う。

> 出典：IPA『ユーザのための要件定義ガイド 第2版』第 6 章（RM.1 立上げ／RM.2 計画／RM.3 監視・コントロール／RM.4 終結）。企業内大規模プロジェクト前提の項目（調達契約・体制構築・会議体・FP 見積り）は省き、1 名＋AI エージェントの SaaS 開発に転用できる部分だけを再構成した。

## 1. ステークホルダの特定と分析

### 1.1 洗い出し（最初は広めに、後で絞る）

| 観点 | 例（SaaS） |
|------|-----------|
| 直接：対象業務の運用者 | 日々入力する担当者（ROLE-01） |
| 直接：対象システムの運用者 | 野口さん（ROLE-09） |
| 直接：最終利用者 | 顧客企業の管理者・一般会員、B2C ならエンドユーザー |
| 直接：業務の結果で評価される人 | 契約者・決裁者（支払う人）、顧客側の経営層 |
| 間接：関連業務の運用者・顧客・取引先 | 顧客の経理（請求書を受け取る）、顧客の情シス（セキュリティチェック） |
| 間接：外部システム | Stripe、IdP、LINE、メール配信、AI API、会計 SaaS |
| 間接：規制・審査 | 個人情報保護、業界団体、アプリストア審査 |

戦略書の SEG-NN を起点にし、「契約者（決裁者）」「日々使う担当者」「データを見る管理者」「連携先」は別のステークホルダとして分ける。

### 1.2 7 種の要件と「誰に聞くか」

| 要件の種類 | 主な要求者 | 1 名開発での聞き先 |
|-----------|-----------|------------------|
| 経営要件（KPI・法規制・予算・稼働時期） | 経営者 | 企画書 OBJ・戦略書 KPI（転記）。クライアント案件は決裁者 |
| 業務要件（手順・業務フロー・処理量） | 現場リーダー | 顧客の担当者。自分が業務を体験する |
| UI 要件（操作性・環境・デバイス） | 利用者 | 代表顧客 1 名のヒアリングと観察 |
| 外部 I/F 要件（連携手段・頻度） | 関連システム | 各 SaaS の API 仕様・制限（WebSearch） |
| システム要件 | 全員 | 欲しい機能を直接受け取らず「業務上なぜ必要か、他に優れた解はないか」を確認してから |
| プロジェクト要件（予算・納期・体制） | 上位層 | 企画書 §7 制約と自分の稼働時間 |
| 運用要件（バックアップ・保守・リリースの容易性） | 運用組織 | 自分（運用者の帽子で）。observability／customer-support Skill の観点 |

### 1.3 分析と対応方針

- ステークホルダ一覧（`requirements.md` §ステークホルダ）に、役割（意思決定者／実行担当者／相談者／報告先）、**影響度（大中小）**、**関心度（大中小）**、対立関係、ヒアリング／レビュー／合意形成のどれに関与するかを書く
- 影響度・関心度ともに高い人の一声で決定が覆る。先にその人と合意し、低い人には結果を共有するだけにする
- 対立する課題はリッチピクチャで可視化し、合意が難しい課題ほど影響範囲が広いので先に深掘りする（`requirements-process.md` §2.2）

## 2. 要求量の制御（スコープのコントロール）

要求量・スコープの制御は要件定義マネジメントで最も重要な要素である。

### 2.1 発散と収束を時間で区切る

- 前半は**発散フェーズ**：否定せずに聴く、「他にどんな要求がありますか」と漏れなく聴く、「なぜ必要ですか」と源泉を聴く
- 発散の期間を先に決めて合意する（例：各テーマの最初の 1 ターンだけ／Phase 5 の最初の 1/5 だけ）。思いつきが出続ける自分を止める仕組みとして使う
- 後半は**収束フェーズ**：6 基準・MoSCoW・採否（`requirements-process.md` §3.4）で絞る。絞り込みは「優先度が低いので外しました」と一方的に言わず、基準と採点を見せて合意する

### 2.2 ベースラインを先に決める

- 着手前に、企画書の予算・期限から**実現できる要求量の上限（ベースライン）**を決めて合意する。最終局面で「予算に収まらないので減らしてください」と言うのは後出しになる
- 初期は予算額をベースラインにし、業務要件一覧（BZ）が揃ったら「IT 手段の件数 × 複雑度」に切り替える
- 業務要件一覧の採用行数（Must／Should）と先送り・棄却行数を Handoff で報告し、ベースライン超過は PM に見える形にする

### 2.3 機能化しない基準（アドオン判定基準の読み替え）

以下に該当する要求はシステム化せず、採否列に理由を書いて「棄却」か「先送り」にする。

- 見栄えや、1 件 1 分程度の操作性改善だけのための機能
- 年間 2 人日程度の代替策（手作業・既存ツール）で済む要求
- 年間 n 件以下のレアケースで、人手（サポート・手動オペ）で救済できるもの
- 業務フローの見直しで解決するもの（現状にこだわらず代替フローを必ず検討する）
- 1 名運用の手間を恒常的に増やす機能（運用コストが効果を上回る）

### 2.4 取捨の記録

要求事項の取捨の経緯と理由は必ず decision-log に残す。記録がないと蒸し返され、見直し時の材料も失われる。

## 3. 決定済み事項の変更手続き

- 決定済みの要求を大きく変える要望は**当事者間で受け入れない**。影響（作成済み成果物の修正範囲、後工程への影響）と効果（完成システムの価値向上）を比べ、**効果が影響を上回る場合だけ**採用する
- 判定者：PM と発注者（自社プロダクトなら PM が本人に確認）。要件定義開始時に「どの規模の変更は PM 判定が要るか」を決めておく（例：MUST の BZ の追加・削除、UC の追加、NFR の緩和・強化、スコープ表の変更）
- 変更要求は open-questions.md に「変更要求」種別で起票し（起票日・内容・理由・影響範囲・効果・可否・判定者・完了日）、採用したら business-requirements.md §6 変更履歴に書き、**要件定義の成果物まで遡って修正**する。下流で変更を受け入れたら上流文書も直す（Phase 21 の改善サイクル・軽量チェンジサイクルでも同じ）
- 1 名開発では「自分の思いつきの変更」を一度 OQ に書いてから採否を決めるクールダウンとして使う

## 4. トレーサビリティ台帳

- 要件定義の全成果物は ID で結ぶ：OBJ → BZ（目的）→ BZ（手段）→ UC／NFR／ROLE →（Phase 7）F →（Phase 9）S／API／ENT →（Phase 13-16）テストケース／E2E。各正本の表に「親 ID」「下流 ID」列を持つ（document-catalog.md §1）
- **システム化しない要求も台帳に残す**（採否＝棄却／先送り）。台帳から消すと「なぜ無いのか」が追えない
- **フォワード**：BZ の採用行がすべて UC か NFR に落ちているか（実現漏れ）。**バックワード**：親 BZ の無い UC・F が無いか（目的に紐付かない機能は作らない・維持しない）
- ID の記載位置と命名を規約化し、Grep で機械的に照合できる状態にする（requirement-traceability-auditor が Phase 17 で F × E2E を突合するのと同型。Phase 6 では reviewer が BZ × UC を突合する）
- 上流が変わったら台帳で影響範囲を特定してから下流を直す（§3）

## 5. 文書の品質管理（形式品質）

- **作成指針を先に決める**：記述規約（`writing-rules.md`）、各文書の粒度・全件か主要か（`document-guide.md`）、ID 規約。「1 文 100 文字以内」より「主語と述語の関係が分かるように書く」のような構造ルールの方がチェックしやすい
- **初期に重点レビュー**：最初の成果物（上流突合表・業務要件一覧の最初の 10 行）を書いた時点で記述規約と粒度を点検し、後続のブレを防ぐ
- **第三者でも機械的にできる 3 つのチェック**（requirements-reviewer の第 1 パス）：
  1. 文書チェック：document-set.md で作ると決めた文書が全部あるか。無い文書は「作らない理由」が書けるか
  2. 集合チェック：各文書に必須要素があるか（例：BZ 行に測定尺度・採否があるか、UC に事前条件・事後条件・例外があるか、NFR に検証方法があるか）
  3. 整合チェック：文書間で**従属値が一致**しているか（同じ ID に同じ名称）、**重複**が無いか（同名の UC・用語）、**参照元が存在**するか（UC が参照する BZ・ROLE・用語が定義されているか）
- 最初から 100 点の文書は無い。評価して是正するプロセスとして回す。レビュー記録（reviews/）の指摘傾向を PROJECT_LEARNINGS に還流する

## 6. 決まらない要件の扱い

- **識別**：どの BZ がシステム化要求（UC／NFR）に落とせていないかを open-questions.md に「未決要件」として列挙する。終結時点で数件が前提。大量にあるなら進め方の問題
- **影響評価**：システム化しない場合の業務への影響と、決まらないまま進む場合の後工程への影響を書く。当事者が評価しにくいので reviewer（第三者視点）にも見せる
- **取り扱い**（3 択）：
  1. 業務上必須なら、**要件定義を延ばして決める**。延ばした分は後工程も延ばす（開発期間だけ短くするのは悪影響しかない）
  2. 評価の結果、**システム化不要**（利用者が極めて少ない、業務を見直せば手作業で済む）
  3. **いったんスコープから外し**、次サイクルで採否を含めて再検討
- 判定は発注者（自社プロダクトなら本人）が行う。「間違っているかもしれないが今決める。後で間違いが分かれば変更扱いにし、追加コストは自分が持つ」と言い切れるかが基準。言えないなら機能を諦めるか期限を見直す
- **先送り基準**（全部満たすものだけ未決のまま Phase 6 へ進める）：効果とスコープに直接関係しない／関連する業務フロー（UC）は確定している／解決する期日と担当が決まっている
- 先送りした未決は open-questions.md §2 の 5 条件（識別・影響評価・取り扱い・期限と先送り基準・リスク登録）を満たし、PM が risk-register で監視する。**未決の先送りだけを放置することは絶対に避ける**

## 7. 完了判断（Phase 5 → 6 → 7 のゲート）

### 7.1 完了基準

| 区分 | 基準 |
|------|------|
| 合意 | ① 業務を変える要求（To-Be の変革ポイント）に関係者全員の合意がある。不同意があっても実施可能な状態 ② 投資額（開発＋3 年の運用費、コンティンジェンシー 20〜30%）と効果（OBJ・KPI への寄与）が見積もられ、発注者がレビュー済み |
| 成果物 | ① document-set.md で決めた文書が全部あり、Self-Check 済み ② 粒度が document-guide.md の基準に達している ③ 達していない文書があれば後工程への影響が無視でき、対応が次フェーズの計画に入っている |
| 残課題 | ① 業務要件の未決はすべて解決、または影響が限定的で解決期日・担当が決まっている（§6 の先送り基準） ② システム化要求の未決も同様 ③ 未決の解決と要件への反映が次フェーズの作業に織り込まれている |

### 7.2 完了判断の材料（Handoff に書く）

- 投資側：開発費（Phase 7 の cost-estimate で確定するが、ここで概算）、運用費（月額ランニング × 36 ヶ月）、自分の稼働時間
- 回収側：OBJ・KPI の目標値と測定方法、定性効果（顧客の声・リスク低減）
- リスク：決まらない要件、上流差し戻し候補、技術的実現性の不安
- **投資額・回収額を甘く自己査定していないか**を疑う。承認を得たい心理で甘くなる。疑義があれば解消するまで完了判断を延ばす

### 7.3 中止・棚上げも選択肢

- 成果物が揃っても「どうも自信が持てない」なら、何らかの問題が潜在している。関係者（reviewer・PM・発注者）で問題がないことを確認し、確認できなければ**施策を棚上げする**選択肢を Handoff に書く
- 要件定義の最大の目的は、着手するか中止するかを正しく判断できる材料を渡すこと。自己資金の 1 名開発ではサンクコストで続けがちなので、Phase 6 Approve 後の Phase 7 着手判断に「中止・縮小の選択肢を検討した」ことを記録する
- 完了して要件が確定した後の変更は、すべて変更要求として §3 で管理する。後になるほど費用と期間は級数的に増える

## 8. 投資効果の見積り（Phase 5 時点の概算）

- 投資側＝初期開発費＋稼働後 3 年（変化の速いフロント系は 1〜2 年）の運用・保守費。要件定義段階では不測の要件拡大に備えてコンティンジェンシーを最低 20〜30% 乗せる
- 効果側＝定量（売上増・コスト削減の 3 年累積）＋定性。**定性効果を無理に定量換算しない**。定性は評価項目（売上への貢献／競争力／品質・サービス／働き方／リスクへの備え）を 5 段階で評価し、受益者（顧客・自分）の平均と「達成責任のコミットメント」で客観性を担保する
- 決裁者への説明は Before/After 図 1 枚（`requirements-process.md` §3.6）。戦略書 §4.3 のユニットエコノミクスと矛盾しないことを確認する
