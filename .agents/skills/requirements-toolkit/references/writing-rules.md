# 要件記述規約（あいまい排除ルール、v0.17.0）

要件定義書・業務要件一覧・ユースケース・非機能要件・用語集など `docs/03-requirements/` 配下の**全文書に適用する記述規約**。requirements-architect はドラフト前に本規約で推敲し、requirements-reviewer は本規約を Grep と精読の判定基準にする。あいまいな要件文は設計・テスト・本稼働の各段階で手戻りコストが膨らむ（要件定義で摘発した欠陥を 1 とすると、システムテストで摘発した場合は約 13 倍）。

> 出典：IPA『ユーザのための要件定義ガイド 第2版』5.1.1「文章のあいまいさを排除し要求を正しく伝達する」、事例 3「図表を使った記述による要件定義文章の品質向上」。本フレームワーク向けに要約・再構成。

## 1. 文の書き方（11 原則）

| # | 規約 | 悪い例 → 良い例 |
|---|------|---------------|
| 1 | **抽象語は定義してから使う**。特に「〇〇管理」は何をすることかを書く。業界用語・社内用語・辞書と異なる意味の語は用語集（glossary.md）に登録する | 「会員管理機能」→「会員の登録・変更・退会・検索・CSV 出力を行う機能（詳細は F-… ）」 |
| 2 | **一文一義・短文**。1 文は平均 40 文字、最長 200 文字、3 行を超えない | 「…であり、…のため、…する」→ 3 文に分ける |
| 3 | **単文主義**。重文（A であり B である）・複文（A のため B する）は分ける | |
| 4 | 冗長・回りくどい・あいまい・嘲笑的な表現を使わない | 「基本的には」「原則として」（例外を書かないなら削る） |
| 5 | **「である調」で統一**。「ですます調」「体言止め」を混在させない | |
| 6 | 列挙は箇条書きにする | |
| 7 | 表にできるものは表にする（条件 × 動作はデシジョンテーブル） | |
| 8 | 図にできるものは図にする（Mermaid：flowchart / stateDiagram / erDiagram） | |
| 9 | **数量は等号・不等号で書く**。「以上／より大きい／以下／未満」は `≧ ＞ ≦ ＜` を併記する | 「100 件以上」→「件数 ≧ 100」 |
| 10 | 漢字とかなの比率はおよそ 1：2。漢字が 5 割を超えると読みにくい | |
| 11 | **形容詞・副詞には数値の補足を付ける** | 「大量のデータ」→「レコード数 ≧ 100 万」／「高速に応答」→「p95 応答時間 ≦ 1.5 秒」 |

## 2. 助詞の規約

- 「は」「が」「の」「を」「に」「まで」を一文の中で連続させない（「進捗会議が時間が来るまで続いた」→「進捗会議は時間が来るまで続いた」）
- **接続助詞「が」を使わない**。「…だが、…」は 2 文に分けるか「しかし」「については」「であっても」で意味を確定する（読み手に 4 通りの解釈を強いる助詞）
- 格助詞「の」の連続（「演算命令の再度の実行の場合の…」）は動詞に戻して書き直す

## 3. 書き言葉を使う（口頭言語の禁止）

| 使わない | 使う |
|---------|------|
| じゃない／そんな／やっぱり／みんな／いろんな | ではない／そのような／やはり／みな／いろいろな |
| すごく／ちゃんと／一発で | 非常に／正しく／一回で |
| でも／なので | しかし／このため |
| 見れる／〜みたい／〜というのは | 見られる／〜ようだ／〜というものは |
| 〜けど／〜たら | 〜が（接続助詞以外）／〜なら |

## 4. 禁止語・要注意語（reviewer が Grep する語彙）

### 4.1 無条件に Block（数値・基準・定義のいずれも無い場合）

いい感じに／使いやすく／効率的に／自動的に／最適化／DX／AI 活用／適切に／適宜／必要に応じて／随時／柔軟に／簡単に／スムーズに／速い／軽い／シンプル／直感的／高速／安定／セキュア／堅牢／快適／リアルタイム（周期を書かない場合）

### 4.2 成果・目標の表現で禁止（測定不能）

**「強化」「改善」「向上」「推進」「充実」「見直し」** を目標・成果の述語に使わない。成果は **MEDIC** のいずれかで書き、現状値・目標値・達成時期を添える：

| MEDIC | 意味 | 書き方の例 |
|-------|------|-----------|
| Maintained | 維持 | 解約率を月 2% 以下に維持する（現状 1.8%、2027-03 まで） |
| Eliminated | 廃止 | 紙の請求書発行を廃止する（現状 月 40 枚 → 0、2026-12） |
| Decreased | 削減 | 月次締め作業を 6 時間 → 1 時間に削減する（2027-01） |
| Increased | 増加 | 有料アカウントを 12 → 50 に増やす（2027-06） |
| Created | 創出 | 法人向け年額プランを新設し月 3 件受注する（2027-03 から） |

### 4.3 時期・範囲があいまいな語（Major）

将来的に／いずれ／順次／当面／など／等（列挙が閉じていない場合は「以下に限る」か「他は対象外」を書く）／一部／各種／所定の／関係者（誰か書く）／ユーザー（どのロールか書く。glossary で ROLE に割り付ける）

### 4.4 「現行踏襲」「現状通り」

要求として受け入れない。現行の仕様を具体的に書き下ろし、それが To-Be でも必要な根拠（BZ の目的）を付ける。書けないものはスコープ外か OQ。

## 5. 用語の統一（glossary.md と連動）

- 同じ意味の語は 1 つに決め、**使わないと決めた語は glossary の「禁止語（同義語）」列に登録**する（例：「顧客／ユーザ／利用者／アカウント」→「利用者」に統一、他は禁止語）
- 名前のない分類に名前を付ける（「得意先でない販売先」→「一般販売先」）
- 分類は MECE（漏れなくダブりなく）。「大口／小口／仕入先」のように軸が混在する分類は軸ごとに分ける
- 要件文中の用語は初出で glossary の定義にリンクする（ID＋名称併記ルールと同じ）

## 6. 記法の選択（ビジネスルールを自然言語で書かない）

ビジネスルールは内容に応じて下表の記法を選ぶ。自然言語の長文で書くと抜け・矛盾が入り、レビューでも見つけにくい。

| 書きたい内容 | 記法 | 本フレームワークでの置き場 |
|-------------|------|--------------------------|
| 管理対象（もの・こと）とその関係・多重度 | ER 図（概念レベル） | requirements.md §概念データモデル（Mermaid erDiagram）→ Phase 9 data-model.md で詳細化 |
| 用語の定義・同義語 | 用語定義表 | glossary.md |
| 分類・区分 | 分類表（MECE） | glossary.md または business-requirements.md |
| 項目の存在条件・入力必須条件 | 表（項目 × 条件） | use-cases.md の事前条件、PS-NNN |
| 計算・按分・切り上げ切り捨て | 計算式（変数を定義して書く） | business-requirements.md / PS-NNN |
| 値の有効範囲 | 数直線または値セット表 | non-functional.md / PS-NNN |
| 条件の組み合わせで動作が変わる | **デシジョンテーブル**（条件 Y/–、動作 X/–。全組み合わせを列挙） | use-cases.md 代替フロー、PS-NNN |
| 状態の変化と遷移条件 | **状態遷移図**（Mermaid stateDiagram。推測した遷移は破線相当の注記で区別） | requirements.md §状態遷移（会員・契約・請求など主要管理対象） |
| 期間・期限（〇日以内に〇する） | 期限チャート＋具体日付の例 | business-requirements.md / use-cases.md |
| 誰が何をできるか | **CRUD 表**（ロール × 対象 × C/R/U/D） | permissions-matrix.md |
| アクター別の手順 | 業務フロー（Mermaid flowchart / swim lane） | Phase 7 business-flow.md（要件では UC の基本フローまで） |
| 行為の責任分担 | 責任分担表（RACI） | requirements.md §ステークホルダ |

## 7. 推敲手順（requirements-architect がドラフト提出前に実施）

1. §4 の語彙を Grep し、各出現箇所に数値・定義・ID のいずれかを付けるか削除する
2. 1 文 200 文字超・3 行超の文を分割する（`awk 'length > 400'` 程度で機械的に抽出できる）
3. 「〜が、」を検索し、接続助詞の「が」を解消する
4. 形容詞・副詞（大きい／多い／早い／少ない／十分／適切）に数値補足が付いているか確認する
5. 「等」「など」で終わる列挙に「以下に限る」か「他は対象外」を書く
6. 目標・成果の述語が MEDIC になっているか、現状値・目標値・達成時期が揃っているか確認する
7. 条件が 3 つ以上絡む文はデシジョンテーブルに書き換える
8. 用語の初出が glossary にあるか、禁止語を使っていないかを確認する

Self-Check（L0）の「記述規約」項目には、上記 1〜8 を実施した旨と Grep で残った語の件数（0 件が原則）を書く。
