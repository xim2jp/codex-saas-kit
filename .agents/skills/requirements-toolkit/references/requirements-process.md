# 要件定義プロセス：ビジネス要求 → システム化要求（v0.17.0）

Phase 5（要件定義）を「質問して書く」から、**ビジネス要求定義（BR）→ システム化要求定義（SR）の 2 層**で進める手順に組み替えたもの。requirements-architect はこの順で作業し、requirements-reviewer は各ステップの成果が揃っているかを見る。

> 出典：IPA『ユーザのための要件定義ガイド 第2版』第 3〜5 章（BR.1 獲得／BR.2 分析／BR.3 文書化／SR.1 仕様化／SR.2 確認・評価）。本フレームワークの Phase 1-4（企画・戦略）が IPA の「企画工程」に、Phase 7-9 が「基本設計（外部設計）」に対応する。マネジメント面（ステークホルダ特定・要求量の制御・決まらない要件・完了判断）は `requirements-management.md`、各文書の記載項目は `document-guide.md` を参照。

## 0. 用語（この 5 語を厳密に使い分ける）

| 用語 | 定義 | 書き方 |
|------|------|--------|
| **問題** | あるべき姿と現状との負のギャップ。解決を要する**事実** | 「月次締めに 6 時間かかっている（目標 1 時間）」 |
| **課題** | 問題を解決するために何をすべきか。解決テーマ | 「締め処理の手作業集計を無くす」 |
| **目的** | 達成したい状態の変化。「〜を達成したい」 | 「経理担当の残業を減らす」 |
| **目標** | 目的のマイルストーン。**現状値・達成時期・目標値**を持つ | 「締め作業 6 時間 → 1 時間、2027-01 まで」 |
| **手段** | 目的・目標を実現するために実施すること。「〜を実施したい」 | 「売上データを Stripe から自動取込する」 |

- **要求**＝「〜したい」全般（目的への要求と手段への要求の 2 種類がある）。**要件**＝要求を文書化・仕様化し**ステークホルダと合意したもの**。合意前の記述は要件と呼ばない
- **ビジネス要求**＝業務運用レベルの要求（なぜ・何を業務として変えるか）。**システム化要求**＝それを実現するシステムの機能・非機能の要求
- **検証**＝書かれた要件が要求を漏れなく誤りなく満たしているか。**妥当性確認**＝その要求自体が目的を達成する手段として妥当か。Phase 6 は両方を行う

## 1. 上流から引き継ぐもの（聞き直さない）

IPA は「経営レベルの目的・目標・施策は企画工程で決まっているべきで、要件定義で検討するのは誤り。要件定義では**確認**する」とする。本フレームワークでは：

| IPA の概念 | 本フレームワークの正本 | Phase 5 での扱い |
|-----------|---------------------|-----------------|
| 経営レベルの目的・目標 | `concept.md` §4 達成目標 **OBJ-NN** | 確認して転記。変えたいなら Phase 1 差し戻し |
| 経営施策（与件） | `concept.md` §3 成果物スコープ、`business-strategy.md` §4-5 収益モデル・チャネル | 与件として要求構造の最上位に置く |
| ステークホルダの最上位 | `business-strategy.md` §3 **SEG-NN** | ステークホルダ一覧の起点にする |
| 最終成果の測定尺度 | `business-strategy.md` §6 **KPI-NN** | KGI 側。業務レベル目標の KPI はここで追加 |
| システム化計画書 | 企画書＋戦略書＋`upstream-reconciliation.md` | 突合表が完成してから §2 以降を始める |

## 2. BR.1 ビジネス要求の獲得

### 2.1 現状の把握（As-Is）

- **「現行踏襲」「現状通り」を要求として受け入れない**。現行がどうなっているかを書き下ろし、To-Be でも残す根拠（目的）を付ける
- 既存システム・既存業務がある案件（改修、リプレース、クライアント案件）は、下記の調査メニューから選んで実施し、結果を `requirements.md` §現状 に書く：
  - **現行システムから可視化**：DB スキーマ・コード・設定・ジョブ・連携先から、システム間関連図／構成図／概念データモデル／画面遷移／業務スケジュールを起こす（AI エージェントに任せやすい）
  - **既存資料の発掘**：`docs/00-inputs/materials/` に加え、規程・マニュアル・研修資料・SLA・契約書・問い合わせログ。改訂管理されている規程は「保証された現状」として優先する
  - **現行業務の再学習**：実際に操作する、担当者に弟子入りするつもりで観察する（エスノグラフィー）、代わりにやってみる（シャドーイング）。1 名運用では自分が顧客業務を体験することが最も安価に「一人称の課題」を得る方法
  - **業務シナリオの読み合わせ**：作った As-Is シナリオを関係者と通読し、認識違いを炙り出す
- 新規 SaaS で「現行」が顧客の手作業・Excel・競合製品の場合も同じ。顧客が今どうやって済ませているかをシナリオとして書く（concept §1.4 を起点に具体化）

### 2.2 ステークホルダの特定と関心事

- ステークホルダを 3 層で捉え、**層ごとに関心事が違う**ことを前提に聞く：
  - 経営層・事業責任者：戦略・利益・他社比較・対外的責任
  - マネージャ：全体俯瞰・非定型業務・リスク回避・判断のタイミング
  - 実務スタッフ：定型業務・ムダムラムリ・「大きく変わってほしくない」
- 実務スタッフだけに聞くと操作性要求が噴出して収拾がつかなくなる。経営層の目的に照らして取捨する
- 対立する課題・多くの人が挙げる課題は影響範囲が広く合意が難しい。**リッチピクチャ**（ステークホルダと課題を一枚絵にし、対立・関連を線で結ぶ）で可視化し、そこから重要課題を深掘りする（Mermaid flowchart で十分）
- 一覧の作り方は `requirements-management.md` §1

### 2.3 問題・ニーズ・課題の抽出

- 要求の**源泉（なぜ）**を必ず書く。「問題（事実）」か「ニーズ（市場・顧客の要望）」のどちらから出た要求かを記録する
- **なぜなぜ分析**で原因を掘り、原因によって対処が変わることを確認する（「情報系が使われない」→「探す場所が複数」ならサーバ統合、「情報が多すぎる」なら絞り込み）
- **すべての原因を解決しようとしない**。ボトルネックになっている原因、効果の大きい原因を 1〜2 つ選んで課題にする。これが要求の膨張を防ぐ最初の関門
- 成果物：`business-requirements.md` の「問題・課題」節（問題 ID／事実／源泉／真因／課題）

### 2.4 ゴールの確認と業務レベル目的・目標の抽出

- 経営レベルの目的は OBJ-NN を確認するだけ。要件定義で新たに立てない
- **業務レベルの目的・目標（サブゴール）を必ず置く**。「経営目的 → （無し）→ システム機能」の**中抜け**は、経営の意図と違うシステムや業務が変わらないシステムを生む
- 抽出はトップダウン（OBJ から部門・業務単位に分解）とボトムアップ（現場の課題から）の併用
- 経営レベルの目的の語彙（分類に使う）：売上を上げる／コストを下げる／品質を上げる／納期を守る／顧客満足度を上げる／安全性を上げる／リスクを下げる／モチベーションを上げる／コンプライアンスを守る／環境・社会貢献
- 成果物：`business-requirements.md` の BZ 行（目的＋目標。目標は現状値・目標値・達成時期）

### 2.5 手段の抽出

- 手段には**業務手段**（人がやる・運用で補う・ルールを変える）と **IT 手段**（システムで実現）がある。IT 手段だけを集めない
- 問題から直接解決策に飛ばず、**一度目的に戻ってから手段を考える**（「手作業集計 → 自動集計機能」ではなく、目的が「情報提供の速さ」なら「集計前データを即時公開」「BI ツール」も候補）
- 手段同士の関係を **and（全部必要）／or（どれか 1 つ）** で明示する
- **作らない手段**（運用・サポート・既存 SaaS で済ます）を必ず候補に入れる。1 名開発ではコードを書かない選択肢が最大のコスト削減になる
- 成果物：BZ 行の「手段」列。IT 手段は Phase 7 で F-NNN に展開される

## 3. BR.2 ビジネス要求の分析

### 3.1 要求の体系化（要求構造図）

- 全要求を「目的」「手段」に分け、**OBJ → 業務目的（BZ）→ 手段** の階層に構造化する（Mermaid flowchart）
- **妥当性の検証（下 → 上）**：この手段はこの目的に効くか。投資額と効果を数値で比べる。合わないなら「本当の目的は別にないか」を掘る（「3 時間削減」→「顧客への早期提供」→「機会損失の低減」）
- **十分性の検証（上 → 下）**：この手段群だけで目的は達成できるか。足りない手段はないか
- 両方向の検証で、目的に合わない要求を落とし、足りない要求を足す。ここで初めて要求の総量が決まる
- 成果物：`requirements.md` §要求構造

### 3.2 測定尺度（KGI / KPI）

- 「向上したい」で止めない。**いつまでに・どれだけ**を書く
- 測定尺度は**間接的でもよいので、自分でタイムリーに測れる定量値**を選ぶ（顧客満足度 → クレーム数／対応時間／返品数／リピート率）。SaaS では PostHog・Stripe・Sentry から自動取得できる値を優先する
- **KGI**＝目的側の尺度、**KPI**＝手段側の尺度（活動が期待どおり行われているか）。戦略書の KPI-NN と重複しないよう、業務レベルの KPI はここで追加し ID を振る
- 成果の述語は MEDIC（維持・廃止・削減・増加・創出）。「強化」「改善」は禁止（`writing-rules.md` §4.2）
- （任意）企画の OBJ と機能を結ぶ**リザルトチェーン**（IT 施策 → 機能 → 業務への影響 → 中間成果 → 最終成果。前提条件とマイナス影響の打ち消し施策も書く）を描くと、Phase 17 トレーサビリティ監査の背骨になる

### 3.3 要求の具体化（To-Be の業務モデル）

要件定義の段階で、業務を 3 つの観点でモデル化する。詳細設計ではなく**業務ルールを確定するため**に描く。

- **情報構造**：管理対象（会員・契約・請求…）の種類を **MECE** に整理し、使わない分類は廃止、重複する分類は統合、名前のない分類に名前を付け、同義語は 1 つに統一して他を**禁止語**にする（→ `glossary.md`）。その上で**概念データモデル**（Mermaid erDiagram、エンティティと多重度のみ）を描き、多重度を業務ルールとして読む（「正社員は複数プロジェクトに同時所属できる」）。Phase 9 の data-model.md はこれを詳細化する
- **ビジネスプロセス**：業務フローに**問題・課題の欄（As-Is）／要求の欄（To-Be）**を設け、課題 ID・要求 ID を書き込みながら To-Be を作る。プロセス見直しの 4 観点＝**廃止**（システム化を人手運用に戻すことも含む）／**集約**（似て非なる処理を 1 つに）／**連結**（複数人の受け渡しを 1 人に）／**並行化**。本フレームワークではフローの正本は Phase 7 business-flow.md だが、要件では UC の基本フローと To-Be の変革ポイントまで確定する
- **相互作用（状態遷移）**：主要管理対象（会員・サブスクリプション・請求・申請など）の**状態遷移図**を描き、遷移条件の抜けと矛盾を確認する。ルールに無く推測した遷移は注記で区別し、レビューで確認する
- **業務パターン表**：顧客区分 × 商品 × 契約形態 … の組み合わせごとに「どのプロセスを辿るか」と発生頻度を表にする。**上位 2 割のパターンで業務量の 8 割**を賄うのが普通で、残り 8 割のパターンは開発難易度が高く品質も出にくい。滅多に無いパターンは**統合するか、業務運用（サポート・手動）でカバー**し、MVP から外す根拠にする
- 業務の複雑さはアーキテクチャでは解けない。要件定義で業務自体を標準化・単純化することが先

### 3.4 優先順位付け

- 判断基準（6 つ）を明示し、**評価は要求の提示元が行う**（第三者には要求の中身が分からない）：

| 基準 | 見るもの |
|------|---------|
| 有効性 | 目的・目標への貢献（定量効果は算出根拠付き、定性効果） |
| 必要性 | 法制度・内部統制・社会的責任・将来性（効果が低くてもやるもの） |
| 緊急性 | 期限が決まっているか（法改正日、拠点開設日、イベント） |
| 費用 | 開発費だけでなく運用費（1 名運用の手間、月額ランニング） |
| 実現性 | 技術的（実績の少ない技術のリスク）・人的（自分で作って運用できるか）。リスクが高いものはスコープから外すのも立派なリスク管理 |
| 新たな問題 | この手段を実現すると生まれる新しい問題と、その対処コスト |

- **粗く 3 段階で判定 → 境界線上のものだけ詳細に調べる**。全要求を精査しない
- 総合判定は **MoSCoW**（Must／Should／Could／Won't）。採点方式にする場合は 5 点満点・コストは低いほど高得点・目安は 3 段階・カテゴリ小計を出す
- 要求一覧には**優先度列と採否列を分ける**。「優先度は低いが採用」「優先度は中だが次期に先送り」を表現できるようにする
- 成果物：`business-requirements.md` の優先度・MoSCoW・採否列

### 3.5 要求を捨てる・先送りする

- 優先順位を付けるだけで終わらせず、**捨てる努力**をする。シンプルでスリムなシステムの方が変化に強い。難しい判断ロジックは**人が運用で対応する方が安くて柔軟**なことが多い（AI 機能の作り込みにも当てはまる）
- **先送り**はリーンスタート的に正当な判断。100 点ではなく 60 点のシステムで出し、使われ方を見て育てる（Phase 19-21 の円環がそのための仕組み）
- 捨てた要求・先送りした要求は削除せず、採否列に「棄却（理由）」「先送り（次期候補）」として残す（蒸し返し防止。decision-log にも記録）

### 3.6 交渉と合意形成

- 要件定義は合意形成プロセス。合意の相手が要件定義に参加していない人（顧客の上長、現場）であることを前提に資料を作る
- **経営者・決裁者向け**：A4／A3 一枚の **Before/After 図**（狙い／予測効果（定量）／現状と問題点／改革後の姿／主な変革ポイント 3 つ／前提条件／要検討事項）。業務フロー全部を見せない。要件定義の最大の目的は「**着手するか中止するかを正しく判断できる材料**を決裁者に渡すこと」
- **業務部門向け**：As-Is は問題・課題のある所、To-Be は要求で変わる所だけを業務フローで説明する
- 合意の作法：ユーザーの「はい」を同意と取らない。復唱して能動的な反対を求める（anti-patterns 兆候 11）。声の大きい人の意見は 6 基準の採点で相対化する
- **レビューをセレモニーにしない**：To-Be フローに沿って業務を**シミュレーション**し、例外業務まで通るかを確かめる。レビューは誤りを見つける場で、解決策を議論する場ではない（検出と対策を分ける）
- クライアント案件では、意見衝突時のエスカレーション先（決裁者）を要件定義の計画段階で決めておく

## 4. BR.3 文書化 → SR.1 仕様化

- 獲得・分析の途中で部分的に書いたものを、最後に**漏れなく完成させる工程**を取る（書きながら進めた文書は穴が残る）
- 文書は `docs/99-pm/document-set.md` で採用したものだけを作る。各文書の記載項目・粒度は `document-guide.md`
- 文書間の関連（どの文書のどの項目が、どの文書を参照するか）を `requirements.md` §文書構成 に書く。不整合の大半は関連を理解していないことから起きる
- SR で確定するもの：ユースケース（`use-cases.md`）、非機能要件（`non-functional.md`）、ロールと CRUD（`permissions-matrix.md`）、用語（`glossary.md`）、未決事項（`open-questions.md`）。画面・API・詳細データモデルは Phase 9
- 記述は `writing-rules.md` に従う。ビジネスルールは自然言語の長文で書かず、記法選択表（同 §6）に従って表・式・図にする

## 5. SR.2 検証と妥当性確認（Phase 6 への引き渡し）

- requirements-architect は提出前に**自分で検証**する：記述規約の推敲手順（writing-rules §7）、文書間の ID 整合、BZ → UC → NFR → ROLE のたどり、採否列と MVP スコープの一致
- requirements-reviewer は**検証**（要求を漏れなく誤りなく書いているか）と**妥当性確認**（要求が OBJ・SEG に効くか）の両方を行う。レビュー観点は過去案件の欠陥傾向（`PROJECT_LEARNINGS.md`、bug-escape-ledger）から更新する
- **全体俯瞰から始める**。詳細の誤字より、文書間の不整合・仕様漏れ・目的不適合を先に探す。全体俯瞰の中間生産物：CRUD 表（ロール／機能 × エンティティ）、業務 × 状態の対比表、（改修なら）新旧対比表
- **妥当性確認は補助資料で行う**：顧客に ER 図を見せず、具体的な数値例（受注 120 個 → 当月出荷 110 個 → 請求 …）やラフスケッチで確認する。**抽象化（汎化）は合意の後**で行う
- 決まらない要件の扱いと完了判断は `requirements-management.md` §4-5

## 6. Phase 5 の進め方（まとめ：成果物の作成順）

```
0. upstream-reconciliation.md（突合）                 ← 対話前に完成
1. requirements.md §現状・§ステークホルダ（As-Is・3 層・対立）
2. business-requirements.md 問題・課題 → BZ（目的・目標・手段・源泉）
3. requirements.md §要求構造（OBJ → BZ → 手段。妥当性・十分性）
4. glossary.md（管理対象の MECE 整理・禁止語）／requirements.md §概念データモデル・§状態遷移
5. business-requirements.md 優先度（6 基準・MoSCoW・採否）→ requirements.md §機能スコープ（MVP／先送り／棄却）
6. use-cases.md／permissions-matrix.md／non-functional.md（SR）
7. open-questions.md／decision-log.md（随時）
8. writing-rules §7 の推敲 → Self-Check → Handoff（上流差し戻し候補・決まらない要件）
```

対話は 1 ターン 3 問以内・5 問ごとに復唱（requirements-architect の Hard Rules）を維持したまま、上の順に進める。質問バンク（`question-bank-*.md`）は各ステップで必要な問いを選ぶための素材で、全部聞くものではない。
