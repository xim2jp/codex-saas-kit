# Completeness Checklist（v0.17.0）

要件定義書ドラフトに進む前、および Phase 6 に引き渡す前に、全項目が「確認済」または「N/A（理由明記）」になっていることを確認する。曖昧なまま進めることは禁止。requirements-architect がドラフト前にユーザーと一緒に埋め、requirements-reviewer が判定基準に使う。

各項目に以下のいずれかを記入：
- ✅ 確認済（内容を 1 行で要約。該当文書・ID）
- ⚠️ 部分確認（不足部分を明記）
- ❌ 未確認
- N/A（適用外。理由を明記）

## 0. 上流からの引き継ぎ（聞き直していないか）

- [ ] 企画書・戦略書が Approve 済みで、`upstream-reconciliation.md` が対話前に完成している
- [ ] 達成目標 OBJ・ターゲット SEG・ビジネスモデル・チャネル・KPI 目標・営業ポータル要否・撤退条件・法規制が ID 付きで転記され、出所が書かれている
- [ ] 企画・戦略との矛盾・上流欠落はすべて OQ になり、上流差し戻し候補（Phase 1／3）が Handoff に書かれている
- [ ] 企画で決まったことを要件定義で独自に書き換えていない

## 1. ステークホルダ（BR.1 / RM.1）

- [ ] 直接（運用者・利用者・評価者）と間接（関連業務・取引先・外部システム・規制）のステークホルダが一覧化されている
- [ ] 各ステークホルダに役割（意思決定者／実行担当者／相談者／報告先）・影響度・関心度がある
- [ ] 7 種の要件（経営・業務・UI・外部 I/F・システム・プロジェクト・運用）それぞれを誰に聞いたか／どこから転記したかが分かる
- [ ] 意思決定者（最終承認者）が特定され、その人が今の議論に同意しそうか確認した
- [ ] 対立する課題（リッチピクチャ）を把握している

## 2. 現状・問題・課題（BR.1）

- [ ] As-Is の業務シナリオが書かれている（顧客が今どう済ませているか）。「現行踏襲」を要求として受け入れていない
- [ ] 問題は事実と定量値、影響は定量値、原因は真因 1 つ、課題は解決テーマとして区別されている
- [ ] 要求の源泉（問題かニーズか）が各 BZ に書かれている
- [ ] 過去の類似試行があれば、その失敗要因を踏まえている

## 3. 目的・目標・手段（BR.1 / BR.2）

- [ ] OBJ → 業務目的（BZ）→ 手段の階層に中抜けがない（経営目的と機能だけで業務目的が無い状態になっていない）
- [ ] 目的系 BZ の全行に測定尺度・現状値・目標値・達成時期がある。述語は MEDIC（強化・改善・向上は無い）
- [ ] 測定尺度は自分でタイムリーに測れる値で、KGI（目的）と KPI（手段）が区別されている
- [ ] 手段に業務手段（人・運用・ルール）が含まれ、全部 IT 手段になっていない。and／or が明示されている
- [ ] 妥当性（手段が目的に効くか）と十分性（手段群で目的が達成できるか）の双方向で検証した
- [ ] コア要件（Must）と加点要件（Should/Could）が分離され、採否列が全行埋まっている
- [ ] 棄却・先送りした要求が理由付きで残っている（削除していない）
- [ ] 問題 ⇄ 要求の照合で、対応の無い問題・源泉の無い要求が 0 件または OQ

## 4. 業務の具体化（BR.2）

- [ ] 管理対象が MECE に分類され、同義語が統一され、禁止語が glossary にある
- [ ] 主要エンティティの概念データモデル（多重度）がある。多重度を業務ルールとして読める
- [ ] 主要管理対象（契約・会員・請求など）の状態遷移図があり、推測した遷移が区別されている
- [ ] 業務パターン表があり、上位 2 割のパターンで業務量の 8 割を賄うこと、レアパターンの運用カバーが決まっている
- [ ] To-Be の変革ポイント（廃止・集約・連結・並行化）が明示され、現状追従になっていない

## 5. システム化要求（SR.1）

- [ ] UC 一覧が業務領域ごとに全件あり、人手のみの作業も残っている
- [ ] 採用 UC の全件に主アクター・事前条件・事後条件・基本シナリオ・例外シナリオ・扱うエンティティ（CRUD）がある
- [ ] 例外・特殊処理の抽出（5W2H／入力ミス・二重操作／期間またぎ／運営者不在／外部障害／サービス時間外／キャンペーン・返金）を全 UC に当てた
- [ ] 業務ルールが表・式・デシジョンテーブル・状態遷移で書かれている（自然言語の長文になっていない）
- [ ] ロール（ROLE）が定義され、ロール × UC、ロール × エンティティ × CRUD があり、CRUD の抜け（登録 UC の無いエンティティ等）が 0 件
- [ ] 外部インターフェース（Stripe・IdP・メール・LINE・AI API・CSV）が接続先・方向・既存/新規・方式・タイミング付きで一覧化されている
- [ ] 保存期間・データ量（NFR）と個人情報の取得項目（SEC）が決まっている

## 6. 非機能要件（SR.1）

- [ ] §0 ビジネス領域の要求（提供先・時間・利用者数・業務継続・業務量・運用方針・セキュリティ方針）が埋まっている
- [ ] 6 カテゴリ（AVL／PERF／OPS／MIG／SEC／ENV）すべてに行があり、全行が数値・レベル値・列挙または「対象外（理由）」
- [ ] 性能・可用性に条件（業務・時間帯・ピーク）が付き、一律値になっていない
- [ ] Tier A 既定値との差分に理由がある。1 名運用で守れない値を約束していない
- [ ] 全行に検証方法（どのテスト・監視・演習で確認するか）がある
- [ ] 運用（サービス時間・計画停止・サポート SLA・運用スケジュール）と移行（公開方式・データ取込・切り戻し・エクスポート）の方針が決まっている
- [ ] 想定規模が戦略書の SOM・ローンチ計画と桁で合っている
- [ ] 外部依存の障害時方針（Stripe・AI API 停止時）が決まっている

## 7. 制約条件

- [ ] 予算上限と月額ランニング上限（一括払いのみ・借入不可）が把握されている
- [ ] 期限とその根拠が明確
- [ ] 投入可能な稼働時間・人員が特定されている
- [ ] 利用必須・利用禁止のベンダー/技術が把握されている
- [ ] 法規制・コンプライアンス要件が洗い出されている（戦略書 §8 からの転記＋追加）
- [ ] 社内承認プロセスの段取りが見えている（クライアント案件）

## 8. スコープ境界

- [ ] 「今回やらないこと」が明文化され、企画書 §5 と矛盾しない
- [ ] 将来拡張余地（先送り BZ）が整理されている
- [ ] 既存システム・外部サービスとの責任分界点が定義されている
- [ ] 営業ポータル要否・モバイル・LINE・MCP・法務文書の含む/含めないが企画書 §3・戦略書 §5.3 から転記されている
- [ ] 要求量がベースライン（予算・期限）に収まっている。超過分は先送り・棄却になっている

## 9. 受け入れ基準・撤退条件・テスト観点

- [ ] 「完成した」と判断する具体的条件（検収・UAT の合格ライン）が具体化されている
- [ ] 受入テスト観点（通常／異常／例外／特殊）とサイクル（日次・月次・年次：請求確定・トライアル終了・年次更新）が列挙されている
- [ ] パイロット運用（スモールスタート）の期間・評価方法が決まっている
- [ ] 撤退ライン・ピボット判断基準が戦略書 §7 から転記されている
- [ ] 契約上の責任範囲（SLA・瑕疵担保）の基本方針が確認されている（クライアント案件のみ）

## 10. マネジメント・完了判断（RM）

- [ ] 決まらない要件が OQ に全件列挙され、影響評価・取り扱い（延長／不要／スコープ外）・先送り基準・期限・担当がある
- [ ] 決定済み事項の変更ルール（何を PM 判定にするか）が決まり、変更は OQ → decision-log → 遡って修正、の手順で記録されている
- [ ] トレーサビリティ：採用 BZ がすべて UC か NFR に落ちている（フォワード）。親 BZ の無い UC が無い（バックワード）
- [ ] 投資側（開発費＋3 年運用費＋コンティンジェンシー 20〜30%）と回収側（OBJ・KPI・定性効果）の概算が Handoff にある。甘い自己査定を疑った
- [ ] 中止・縮小・棚上げの選択肢を検討したことが記録されている
- [ ] 文書セット（document-set.md）で作ると決めた文書が全部あり、無い文書には理由がある

## 11. メタ確認（記述品質）

- [ ] 曖昧語（writing-rules §4.1〜4.3）が Grep で 0 件、または数値・定義・ID が付いている
- [ ] 1 文 200 文字超・接続助詞「が」・口頭言語が残っていない（writing-rules §7 の推敲手順を実施）
- [ ] 仮定として置いている事項がリストアップされ、ユーザーに確認済み
- [ ] 5 問ごとの復唱でユーザーから能動的な合意（「違ったら止めてください」への無反応ではなく明示の承認）を得ている
- [ ] 自分の好む技術への誘導が起きていないか、anti-patterns.md で点検済み
- [ ] 全文書に Self-Check（L0）と Handoff がある

## チェックリストの使い方

1. 全ステップ（requirements-process.md §6 の作成順）の対話が終わった時点で、このチェックリストを開く
2. 各項目をユーザーと一緒に埋める（声に出して読み上げ、状態を確認）
3. ❌ や ⚠️ がある項目は、追加質問で潰す。潰せないものは OQ にして §10 の先送り基準を満たすか確認する
4. 全項目が ✅ または明示的 N/A になったら、要件定義書ドラフトを確定し Phase 6 へ渡す
