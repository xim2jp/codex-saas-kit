# Completeness Checklist

要件定義書ドラフトに進む前に、全項目が「確認済」または「N/A（理由明記）」になっていることを確認する。曖昧なまま進めることは禁止。

各項目に以下のいずれかを記入：
- ✅ 確認済（内容を1行で要約）
- ⚠️ 部分確認（不足部分を明記）
- ❌ 未確認
- N/A（適用外。理由を明記）

## 背景・目的

- [ ] このプロジェクトを今やる動機が明確
- [ ] やらない場合の影響（痛みの大きさ）が定量または定性で表現できる
- [ ] 過去の類似試行があれば、その失敗要因を踏まえている
- [ ] 意思決定者と現場担当者が特定されている

## 利用者・現状

- [ ] 主たる利用者の役割・人数・スキルレベルが特定されている
- [ ] As-Is業務フローが把握されている
- [ ] 関係する既存システム・データソースが洗い出されている
- [ ] データの所在・形式・権限管理が把握されている

## 理想状態・成功基準

- [ ] To-Be業務フローの輪郭が描けている
- [ ] 成功を測る具体的な指標（KPI）が1つ以上ある
- [ ] コア要件（MUST）と加点要件（NICE TO HAVE）が分離されている
- [ ] 成功した姿を関係者間で共有できる粒度になっている

## 制約条件

- [ ] 予算上限と内訳構造が把握されている
- [ ] 期限とその根拠が明確
- [ ] 投入可能な人員（社内・社外）が特定されている
- [ ] 利用必須・利用禁止のベンダー/技術が把握されている
- [ ] 法規制・コンプライアンス要件が洗い出されている
- [ ] 社内承認プロセスの段取りが見えている

## 非機能要件

- [ ] 同時接続数・想定負荷が見積もられている
- [ ] 可用性要件（許容停止時間）が定義されている
- [ ] セキュリティ要件（認証、暗号化、データ分類）が定義されている
- [ ] バックアップ・災害復旧の要件が定義されている
- [ ] ログ保管期間・監査要件が定義されている
- [ ] 運用保守体制（誰が、どの範囲で）が決まっている

## スコープ境界

- [ ] 「今回やらないこと」のリストが明文化されている
- [ ] 将来拡張余地のリストが整理されている
- [ ] 既存システムとの責任分界点が定義されている

## 受け入れ基準・撤退条件

- [ ] 検収の判定条件が具体化されている
- [ ] パイロット運用の期間・評価方法が決まっている
- [ ] 撤退ラインまたはピボット判断基準が決まっている
- [ ] 契約上の責任範囲（SLA、瑕疵担保）の基本方針が確認されている（クライアント案件のみ）

## メタ確認

- [ ] 曖昧語（いい感じに、効率的に、最適化、等）がすべて具体化されている
- [ ] 仮定として置いている事項がリストアップされ、ユーザーに確認済み
- [ ] 5問ごとの復唱でユーザーから明示的な合意を得ている
- [ ] 自分の好む技術への誘導が起きていないか、anti-patterns.md で点検済み

## チェックリストの使い方

1. 全フェーズの質問が終わった時点で、このチェックリストを開く
2. 各項目をユーザーと一緒に埋める（声に出して読み上げ、状態を確認）
3. ❌ や ⚠️ がある項目は、追加質問で潰す
4. 全項目が ✅ または明示的 N/A になったら、要件定義書ドラフトに進む
