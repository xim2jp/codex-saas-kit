# Resilience Testing Skill

SaaS が**想定負荷に耐え、外部依存が落ちても致命的に壊れない**ことを検証するための知識集。負荷試験（k6）と障害耐性演習（failure scenarios）の2本柱で構成する。

> **このSkillのゴール**：野口さんが1名運用で量産する月額 SaaS が、①想定ユーザー数の負荷で応答性能が破綻しないこと、②Supabase / Stripe / AI API のいずれかが落ちても**サービス全体が道連れで停止しない**ことを、過剰投資なく検証できる状態にする。

## 重要原則

### 1. 野口さんProfile：過剰負荷試験をしない

1名運用・Tier A（Vercel + Supabase）・無料枠優先が前提。**大規模エンタープライズ水準の負荷試験基盤は組まない**。

> **基本方針：MVP は「主要3シナリオ」（通常時の想定同時接続、決済への負荷、想定ピーク時）で十分。網羅的なシナリオマトリクスは、有料プラン移行や契約上のSLAが必要になった段階で拡張する。**

- 無料でできる範囲（k6 OSS ローカル実行、Grafana Cloud k6 無料枠）で完結させる
- 「念のため」で本番相当の高負荷テストを無料枠の Supabase/Vercel に打ち込み、プロジェクト自体をレート制限や請求超過に追い込まない（テスト対象＝本番環境ではなくステージング/プレビュー環境を使う）
- 目標値は**実際の想定ユーザー数**から逆算する。汎用的な「1000 req/sec」等の数値をそのまま採用しない

### 2. 負荷試験と障害耐性は別物、両方必要

| 観点 | 負荷試験（load-testing-k6.md） | 障害耐性（failure-scenarios.md） |
|------|------------------------------|----------------------------------|
| 検証すること | 想定負荷でも性能が破綻しないか | 外部依存が落ちても致命傷にならないか |
| 手法 | k6 でリクエストを大量発行 | 依存を意図的に落とす/遅延させる |
| 失敗の兆候 | レイテンシ悪化、エラー率上昇 | 無関係な機能まで巻き添えで停止 |
| 野口さんMVPでの重み | 中（Tier A は基本スケールするため） | **高**（外部SaaS依存が多く、単一障害点になりやすい）|

野口さんスタック（Vercel + Supabase + Stripe + AI API）は**外部マネージドサービスへの依存度が高い**構成のため、実は負荷試験より**障害耐性のほうが実利が大きい**。両方を「主要3シナリオ」に絞って実施する。

### 3. Graceful Degradation を設計の前提にする

「外部サービスが落ちたら全機能停止」ではなく、**落ちた依存に関係ない機能は動き続ける**ことを目指す。実装フェーズでこの発想を組み込むほうが、後からテストで検出して直すより低コスト。詳細は `failure-scenarios.md`。

## フェーズ別の要点

- **テスト計画**：`docs/40-test-plan/non-functional-tests.md` の性能・耐障害性セクションに主要3シナリオを宣言する。数値目標（想定同時接続数、許容レイテンシ）は案件の想定ユーザー数から具体化する
- **実装**：Supabase・Stripe・AI API の呼び出しにタイムアウト・リトライ・サーキットブレーカー相当を `failure-scenarios.md` の graceful degradation パターンで組み込む
- **テスト実装**：k6 スクリプトは `load-testing-k6.md` のテンプレートを流用する。障害注入（Supabase 停止相当、Stripe API モックエラー等）は Playwright / Vitest レベルで再現する
- **デプロイ前レビュー**：主要3シナリオが検証済みかをチェックリストとして確認する
- **本番運用中**：想定外の負荷増・外部サービス障害の後に事後検証し、シナリオを補強する

## 野口さん固有のチェック

- [ ] 負荷試験の対象が本番環境ではなくステージング/プレビュー環境になっているか
- [ ] Vercel Hobby / Supabase Free の無料枠の制限値（同時接続数、レート制限）を把握した上で目標値を設定しているか
- [ ] Grafana Cloud k6 の無料枠（月500 VUh、14日保持）内で完結する試験規模になっているか、超過する場合はローカル実行に切り替えているか
- [ ] 「Stripeが落ちても既存ユーザーは使い続けられるか」等、必須シナリオ集（`failure-scenarios.md`）が最低限カバーされているか
- [ ] MVP 段階で主要3シナリオ以上に手を広げていないか（過剰投資の兆候）

## アンチパターン（よくある失敗）

1. **本番環境に対して負荷試験を打つ**：実ユーザーへの悪影響、無料枠の制限超過による請求発生・アカウント停止リスク
2. **汎用的な負荷目標をそのまま採用**：「1000 req/sec に耐える」等、想定ユーザー数と乖離した目標で工数を浪費
3. **外部依存の障害を一度も想定しない**：Supabase/Stripe/AI APIのSLAを過信し、落ちた瞬間に全機能停止する設計になる
4. **負荷試験だけやって障害耐性を無視**：野口さんスタックでは後者のほうが実利が大きいのに手薄になりがち
5. **CI に組み込まず一度きりの手動実行で終わる**：性能劣化のリグレッションを検出できない
6. **フォールバック実装のテストをせず「たぶん動く」で済ませる**：実際に依存を落として確認しないと分からない
7. **MVPなのに大規模な負荷試験基盤（分散ロードジェネレータ等）を構築する**：1名運用のコストに見合わない
