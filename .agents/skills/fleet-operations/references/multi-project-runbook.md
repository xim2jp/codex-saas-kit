# 複数SaaS運用ランブック（優先順位付け・インシデント対応・月次棚卸し）

複数の SaaS を1名運用する野口さんが、**同時多発の問題に飲まれず**対応するための手順書。個別SaaSの技術的な障害調査手順（Sentry/New Relic の使い方等）は `observability-integration` の `alerting-and-dashboards.md` に委ね、本書は**どの案件から・誰が・どう対応するか**というポートフォリオレベルの意思決定を扱う。

## 0. 前提：1名運用の限界を最初から受け入れる

> **アラート委任はできない。24時間対応もできない。だから「全部拾おうとしない」ことが本質である。**

複数SaaSが同時にアラートを上げた場合、野口さんが物理的に対応できるのは1件ずつ。**優先順位を機械的に決める仕組み**がないと、声が大きい（＝通知がうるさい）案件から着手してしまい、本当に重要な案件を放置するリスクがある。本書の目的はその事故を防ぐこと。

## 1. 優先順位付けの基準

### 1.1 一次基準：MRR規模

案件を売上規模で階層化し、対応順の既定値とする。

| 階層 | MRR目安 | 対応方針 |
|------|--------|---------|
| **S** | 上位1〜2案件（艦隊の売上の大半を占める） | 最優先。Critical検知後、可能な限り即時着手 |
| **A** | 一定の売上があり継続契約者がいる | Critical検知後、当日中の着手を目標 |
| **B** | 小規模・検証中・無料枠中心 | 翌営業日以降でも許容。放置しても致命傷にならない範囲 |

- 階層は固定ではなく、`fleet-dashboard-design.md` のMRRデータを基に**月次棚卸しの際に見直す**（後述）。
- 階層分けは `fleet_projects` テーブルの `sla_flag` やメタ情報として管理し、ダッシュボード上でも視認できるようにする。

### 1.2 二次基準：契約SLAの有無

MRRが小さくても、**契約でSLA（稼働率保証・対応時間保証）を約束している案件は別枠で最優先扱い**とする。

| SLA有無 | 対応時間目標（Critical） |
|---------|------------------------|
| SLA契約あり（例：99.5%保証・4時間以内対応 等契約書記載の値） | 契約で定めた時間内。最優先で着手 |
| SLA契約なし（大半の自社/小規模案件） | ベストエフォート。1.1のMRR階層に従う |

> SLAを結んでいる案件がある場合、その契約書の対応時間目標を `fleet_projects` にメタデータとして記録し、階層基準より優先させる。

### 1.3 優先順位の決定順

1. SLA契約がありSLA違反が発生・切迫している案件 → 最優先
2. MRR階層 S の案件で Critical 障害 → 次点
3. MRR階層 A の案件で Critical 障害
4. 上記以外（B階層 or Warningレベル）→ 順次対応

同時に複数件Criticalが出た場合は、上記の順に**1件ずつ**着手する。並行対応はしない（中途半端な対応を複数抱えるより、1件を早く収束させる方が結果的に速い）。

### 1.4 判断に迷った時の簡易フローチャート（概念）

```
Critical検知
  └─ SLA契約案件で違反切迫？ ─Yes→ 即着手
       │No
       └─ MRR階層S？ ─Yes→ 他に対応中の案件がなければ即着手
            │No
            └─ MRR階層A？ ─Yes→ 当日中に着手（他S案件対応中なら完了後）
                 │No
                 └─ B階層 or Warning → 翌営業日以降でキューに積む
```

- 迷ったら**MRRとSLAの2軸だけ**で決める。それ以外の感情的な理由（「声をかけられた」「たまたま先に気づいた」）で順番を動かさない。

## 2. インシデント発生時の一次対応フロー

```
検知 → トリアージ → 対応 → 事後報告
```

### 2.1 検知

- 横串ダッシュボード（`fleet-dashboard-design.md`）の Slack 通知、または各SaaSの `observability-integration` アラートから検知
- 検知経路が複数（横串サマリ／個別Sentry／個別New Relic）あるため、**通知には必ず案件名を明記**し、混同を防ぐ

### 2.2 トリアージ（5分以内を目安）

1. 横串ダッシュボードで該当SaaSのステータス（UP/DEGRADED/DOWN）とエラー件数を確認
2. 本書 1章の優先順位基準に照らし、**今すぐ着手するか、後回しにするか**を即断
3. 後回しにする場合は、その旨を明示的に記録（後述のインシデントログ）し、着手予定時刻を決める
4. 複数件が同時発生している場合、着手する1件以外は「保留」であることを自分に明示する（無意識に手が伸びるのを防ぐ）

### 2.3 対応

- 個別SaaSの技術的調査は `observability-integration` の MCP サーバー経由調査（Codex から自然言語で問い合わせ）を用いる
- 復旧の型は案件ごとの `docs/operations/runbooks/`（`observability-integration` 側で整備）に従う
- 本書が扱うのはあくまで「どの順で・どこまで時間を割くか」であり、個別の復旧手順そのものではない

### 2.4 事後報告

- インシデントログ（下記フォーマット）に記録
- 影響が顧客に及んだ場合、該当SaaS側のステータスページ/メールで告知（この告知フローは各案件のカスタマーサポート体制に従う）
- 月次棚卸し（4章）で再発防止策が取られているか確認

### インシデントログ（概念フォーマット）

```markdown
## 2026-07-02 14:20 - SaaS-C DOWN

- 検知経路：横串ダッシュボード Slack通知
- 優先順位判断：MRR階層B、SLA契約なし → 他対応中のS案件を優先し30分保留
- 着手：14:50
- 原因：Supabase接続プールの枯渇
- 復旧：15:10（Vercel再デプロイで接続プールリセット）
- 再発防止：Supabase接続数の監視アラートをobservability-integration側に追加（要implementation-worker）
```

### 2.5 同時多発時のシナリオ例

3案件で同時にアラートが鳴った状況を想定した判断例（あくまで一例。実際は1.4のフローチャートに従う）。

| 案件 | 状態 | MRR階層 | SLA | 判断 |
|------|------|---------|-----|------|
| SaaS-A | DOWN（5xx多発） | S | なし | 即着手（S階層かつ最も影響大） |
| SaaS-B | DEGRADED（レイテンシ増） | A | あり（4時間対応） | SLA違反切迫なら最優先に格上げ、そうでなければA着手後に対応 |
| SaaS-C | Warning（エラー微増） | B | なし | キューに積み、翌営業日確認 |

- SaaS-BにSLAがある場合は1.3節の決定順どおり**SLA案件を最優先**にする。SLA違反までの猶予がまだあるなら、DOWNしているSaaS-Aを先に収束させてからSaaS-Bに着手する判断もあり得る（残り猶予時間と復旧見込み時間を比較して決める）。
- SaaS-Cは放置してよいわけではなく、「今すぐではない」というだけ。キューに積んだ案件は当日中に必ず一度は状況を再確認する。

## 3. 対応できないときの代替手段（1名運用の現実解）

複数同時発生時、または野口さんが物理的に対応不可能な時間帯（睡眠・他案件の商談中等）に発生した場合の現実的な対処。

- **アラート委任は原則不可**：外部委託・チームメンバーへの一次対応委任は前提としない（1名運用のコスト構造上、常時待機要員を置けない）
- **本質は「優先度を絞ること」**：全SaaSに同レベルの即応を約束しない。営業サイトやオンボーディング時点で、SLA契約なし案件には「ベストエフォート対応」であることを明示しておく
- **DOWN検知時の自動フェイルセーフを仕込む**：各案件側でメンテナンスページへの自動フォールバック、Cronジョブの自動リトライ等、`observability-integration` 側の計装で「人が動くまでの時間を稼ぐ」設計を入れておく
- **翌朝一括処理の許容**：夜間発生でSLA対象外の障害は、翌朝の営業開始時に一括でトリアージしても致命傷にならないよう、事前に該当SaaSの性質（バッチ処理中心か、リアルタイム性が必須か）を把握しておく
- **cost-guardian由来のコストアラートは緊急性が低い**：即時対応ではなく月次棚卸しに回してよい（課金停止等の緊急性がある場合を除く）

### 3.1 「対応しない」判断を正式なものにする

優先度を絞るというのは、単に後回しにするだけでなく、**時に「今回は対応しない」と明示的に決める**ことも含む。

- B階層・SLAなし案件のWarningレベルは、月次棚卸しでまとめて確認する運用でよい（都度対応しない）
- 「対応しない」と決めた場合も、インシデントログには必ず記録する（記録がないと、後から「見落とした」のか「意図的に見送った」のか分からなくなる）
- 顧客影響が発生した場合のみ、B階層であっても個別に状況説明を行う（放置＝顧客軽視にならないよう最低限のコミュニケーションは維持する）

## 4. 月次棚卸しルーチン

障害対応とは別に、**月1回・全SaaS横断**で以下をレビューする。個別項目の深掘りは各連携Skillに委ねる。

### 4.1 棚卸し項目

| 項目 | 内容 | 連携先 |
|------|------|--------|
| コスト | 各SaaSのランニングコスト、無料枠の使用率、超過リスク | **cost-guardian**（財務分析はここに委任） |
| 利用状況 | MAU/DAU、主要機能の利用率、休眠ユーザー比率 | `analytics-integration`（PostHog/GA4） |
| 解約率 | 当月Churn、解約理由（把握できていれば） | Stripe（横串ダッシュボードのChurn欄） |
| セキュリティアップデート | 依存パッケージの脆弱性、Next.js/Supabaseクライアント等のメジャーアップデート追従状況 | 各案件の `package.json` / Dependabot等 |
| MRR階層の見直し | 1.1章の階層（S/A/B）を最新MRRで再評価 | 横串ダッシュボード |
| SLA遵守状況 | SLA契約案件で違反がなかったか | インシデントログ |

### 4.2 棚卸しの進め方（概念）

1. 横串ダッシュボードで全SaaSのMRR・Churn・稼働率を一覧確認
2. cost-guardian にコスト超過・無駄なサブスクの有無を確認依頼
3. セキュリティアップデートは案件ごとに `npm outdated` / `npm audit`（または同等ツール）の結果を横断でチェック
4. 今月のインシデントログを振り返り、再発防止策が実施済みか確認
5. MRR階層（S/A/B）を見直し、`fleet_projects` のメタデータを更新
6. 結果を野口さん自身向けの棚卸しメモとして記録（案件側ドキュメントには残さない）

### 4.3 棚卸しチェックリスト

- [ ] 全SaaSのランニングコストを cost-guardian と突合し、無料枠超過・不要サブスクがないか確認した
- [ ] 各SaaSの利用状況（MAU等）を確認し、極端な低下がないか確認した
- [ ] 各SaaSのChurnを確認し、急増している案件があれば原因仮説を立てた
- [ ] 依存パッケージのセキュリティアップデートが放置されていないか確認した
- [ ] MRR階層（S/A/B）を最新値で見直した
- [ ] SLA契約案件で違反がなかったか確認した
- [ ] 今月のインシデントログの再発防止策が実施済みか確認した

### 4.4 棚卸しの頻度と所要時間の目安

- 頻度：月1回（月初 or 月末で固定日を決め、カレンダーに繰り返し予定として登録する）
- 所要時間の目安：艦隊規模が小規模（〜5案件程度）なら1〜2時間程度を想定。案件数が増えるほど横串ダッシュボードの自動集計に頼る比率を上げ、手作業を増やさない
- 棚卸しの結果、MRR階層が変わった案件は、翌月から新しい優先順位で運用する（1.1節の階層は棚卸しのたびに更新される「生きた基準」であることに注意）

## 5. cost-guardian との連携ポイント（まとめ）

- **役割分担**：本Skill（fleet-operations）は「運用状態の可視化・優先順位判断・インシデント対応フロー」を担い、cost-guardian は「費用の妥当性判断・削減提案」を担う
- **データの受け渡し**：横串ダッシュボードのMRR/コスト欄は cost-guardian の算定結果を正とする（`fleet-dashboard-design.md` 3.2節参照）
- **月次棚卸しでの連携**：4.1節のコスト項目は cost-guardian の分析結果を取り込んで判断する。fleet-operations 側で独自にコスト削減の意思決定はしない
- **緊急コストアラート**：無料枠超過が課金停止・サービス停止に直結する場合、cost-guardian からのアラートは Critical 相当として1章の優先順位判断に組み込む

## 6. アンチパターン（ランブック運用でよくある失敗）

1. **通知の音量で優先順位を決める**：うるさいアラートから対応すると、静かに壊れているS階層案件を見逃す
2. **同時に複数案件へ手を広げる**：どれも中途半端になり、結果的に全体の復旧が遅れる
3. **「対応しない」判断を記録に残さない**：見落としと意図的な見送りの区別がつかなくなり、再発時の判断材料が失われる
4. **月次棚卸しを障害が起きた月だけスキップする**：障害対応で忙しい月こそ、コスト・セキュリティの見落としが起きやすい
5. **MRR階層を一度決めたら固定してしまう**：案件の成長・縮小に応じて階層を更新しないと、優先順位が実態とずれる
6. **SLA契約の内容を記憶頼みにする**：契約書を都度確認する運用では緊急時に間に合わない。事前にメタデータ化しておく
