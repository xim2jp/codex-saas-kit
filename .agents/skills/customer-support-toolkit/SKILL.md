# Customer Support Toolkit Skill

野口さんが**1名で複数の月額SaaSを並行運用**しながらカスタマーサポートを破綻させないための知識集。ヘルプセンターの自動生成、AIによる問い合わせ一次応答、FAQの自動更新までを、量産・横展開しやすい形で扱う。

> **このSkillのゴール**：新しいSaaSを1つ立ち上げるたびにサポート体制をゼロから作らず、**docs/ の設計資産とログデータから自動生成・自動更新**される仕組みで、1名運用のまま複数プロダクトの問い合わせ対応品質を維持する。

## いつこのSkillを参照するか

カスタマーサポートは**実装フェーズ以降〜運用フェーズにかけて継続する横断的関心事**である。以下で必ず読む：

- **実装フェーズ（Phase 11 相当）**：ヘルプセンター（`app/help/` 以下）の実装時（→ `help-center-generation.md`）
- **実装フェーズ（Phase 11 相当）**：問い合わせフォーム/受信メールへのAI一次応答機能の実装時（→ `ai-first-response.md`）
- **公開後の運用フェーズ**：問い合わせログからFAQを継続更新する仕組みの構築・運用時（→ `faq-maintenance.md`）
- **新規SaaS立ち上げ時**：既存プロダクトのヘルプセンター/FAQテンプレートを横展開する時（→ 全references）
- **レビュー時**：AI一次応答の誤回答リスク・エスカレーション漏れ・PII取り扱いのチェック（→ `ai-first-response.md` のガードレール節）

## 重要原則（必読）

### 1. サポートは「作る」のではなく「生成する」

1名運用で複数SaaSのヘルプセンターを個別に手書きするのは持続不可能。**要件定義書・機能一覧・画面設計（docs/）を単一の情報源とし、ヘルプ記事を自動生成・自動同期する**のが基本方針。手書きは「生成できない微妙なニュアンス」の加筆修正に限定する。

### 2. AIの一次応答は「答える」より先に「答えて良いか」を判定する

Claude API による自動応答は**回答範囲を明示的に区切り**、範囲外・自信がない・返金や法的判断を伴う問い合わせは即座に人間（野口さん）へエスカレーションする。ハルシネーションによる誤回答は複数SaaSの信頼を同時に毀損するため、**保守的な設計を優先**する。詳細は `ai-first-response.md`。

### 3. 野口さん財務制約：Claude APIコストは無制限にしない

民事再生中・一括払いのみ・借入不可。Claude API は無料枠が存在しないため、**問い合わせ1件あたりのコストを見積もった上で使用量に上限を設ける**（レート制限・月次予算アラート・キャッシュ活用）。ランニングコストが読めないまま複数SaaSに展開しない。

> **基本方針：AI一次応答は「よくある質問への即答」に絞り、複雑な調査・過去ログ全件参照など高コストな処理は人間対応にフォールバックする。**

### 4. 1名運用は「承認フローの軽量化」で回す

FAQ更新もエスカレーション対応も、レビュー・承認者が野口さん1人。多段階の承認フローは不要で、**候補の自動生成 → 野口さんの最終確認 → 即反映**の一段階フローに簡略化する。詳細は `faq-maintenance.md`。

### 5. 複数SaaS間でテンプレートを再利用する

ヘルプセンターの構造（カテゴリ体系・記事テンプレート・検索UI）、AI一次応答のプロンプト骨格、FAQ抽出パイプラインは**プロダクト固有部分とプロダクト非依存部分を分離**し、後者はSaaS間で使い回す。新規SaaS立ち上げ時のサポート整備を数時間〜数日に短縮する。

## エージェント別の使い方ガイド

### implementation-worker

- `app/help/` 以下のヘルプセンタールーティング、記事コンテンツ管理（MDX or Supabaseテーブル）、検索機能を実装（→ `help-center-generation.md`）
- 問い合わせフォームのAI一次応答API Route・エスカレーション判定ロジックを実装（→ `ai-first-response.md`）
- 問い合わせログ収集用のSupabaseテーブル・FAQ候補抽出バッチを実装（→ `faq-maintenance.md`）

### external-designer

- ヘルプセンターの画面一覧・情報設計（カテゴリ階層・検索導線）を `docs/20-external-design/` に反映
- 問い合わせフォームのエラー処理・エスカレーション時のユーザー向け文言を設計

### implementation-reviewer

- AI一次応答の回答範囲逸脱・エスカレーション漏れ・PII混入をレビュー
- Claude API呼び出しにレート制限・コスト上限が実装されているかチェック

### observability-integration-specialist（連携先）

- AI一次応答の誤回答率・エスカレーション率をダッシュボードで監視する場合は `observability-integration` Skill と併用

### cost-guardian（今後追加予定のコスト管理専門エージェント）

- 複数SaaS横断でのSaaSツール・API利用料の一括モニタリングを担う専門エージェントとして別途整備予定。Claude APIの使用量上限設計（`ai-first-response.md`）は将来的にこのエージェントの管轄と接続する想定のため、コスト設計は同ドキュメントの方針に準拠しておくこと。

## 野口さん固有のチェック

- [ ] ヘルプ記事が docs/（要件定義書・機能一覧・画面設計）から自動生成/同期される構成になっているか（手書き一辺倒になっていないか）
- [ ] Claude APIの呼び出しにレート制限・月次予算アラートが設定されているか
- [ ] AI一次応答が回答範囲外の質問を検知し、確実に人間（野口さん）へエスカレーションできるか
- [ ] 返金・解約・法的判断を伴う問い合わせがAI単独で完結しない設計か
- [ ] FAQ更新の承認フローが野口さん1人の最終確認で完結する軽量設計か（多段階承認になっていないか）
- [ ] ヘルプセンター/AI一次応答/FAQテンプレートが他のSaaSプロダクトへ横展開しやすい構造か
- [ ] 問い合わせログにPII（氏名・メール・決済情報等）が含まれる場合、保存・AI送信時の取り扱いが適切か

## アンチパターン

1. **SaaSごとにヘルプセンターを手書きでゼロから作る**：1名運用では継続更新が破綻する
2. **AIに回答範囲の制約を設けず全問い合わせに自動応答させる**：誤回答が複数SaaSの信頼を同時に毀損する
3. **エスカレーション基準を定義しない**：AIが答えられない質問を無理に答えてしまう
4. **Claude API呼び出しに使用量上限を設けない**：無料枠がないため想定外のコストが積み上がる
5. **返金・解約・契約関連をAIが単独処理**：金銭・契約に関わる判断は必ず人間を介在させる
6. **FAQ承認フローを多段階にする**：1名運用では承認者が野口さん1人なので不要な重さになる
7. **問い合わせログを分析せず放置**：頻出質問がFAQに反映されず同じ問い合わせが繰り返される
8. **ヘルプ記事とdocs/の内容が乖離する**：機能追加時にヘルプセンターだけ更新漏れになる
9. **AI一次応答のプロンプトをSaaSごとに作り直す**：プロダクト非依存部分を切り出さず量産効率が出ない
10. **PIIを含む問い合わせ内容を無制限にAIへ送信・ログ保存する**：取り扱い方針を決めずに実装してしまう
