# Feedback Loop（還流ループ）運用ガイド

各案件で得た知見を、フレームワーク本体に確実に還流させる仕組み。

## 中核思想

**「コピーすれば自由、しかし還流しなければ本体は死ぬ」**

フレームワークが成長し続けるためには、案件で得た学びを系統的に本体に戻す規律が不可欠。

## 4層の還流メカニズム

### 層1：案件側での記録（日常的）

各案件のルートに `PROJECT_LEARNINGS.md` を配置し、**気付いたその場で書く**。

記録すべきもの：
- エージェントの応答で違和感があった点
- 不足していたチェック項目
- 既存Skillに追記したい知見
- 新しいエージェントの必要性
- 案件固有の制約・条件

**重要**：書き溜めるのは禁物。**気付いた即日に書く**。記憶は2日で半減する。

### 層2：月次レビュー（規律的）

毎月最終金曜（または月末日）に：

1. 各案件の `PROJECT_LEARNINGS.md` をすべて開く
2. 「本体に還流すべき」項目を抽出
3. 本体リポジトリに Issue として登録（テンプレ使用）
4. 重要度・緊急度で優先順位付け

詳細手順: `docs/operations/monthly-review.md`

### 層3：本体への反映（実装的）

優先順位の高いものから：

1. Issue → PR
2. `.codex/` / `.agents/` の該当ファイルを修正
3. CHANGELOG.md に記録
4. セマンティックバージョニングでタグ付け
5. `docs/learnings/YYYY-MM-<project>.md` にも整理

### 層4：既存案件への配信（機構化）

新バージョンが出たら：

1. `docs/projects/INDEX.md` の「配布先ローカルパス」節に案件が登録されていることを確認
2. `bash scripts/export-to-projects.sh --dry-run` で対象と現在バージョンを確認
3. `bash scripts/export-to-projects.sh` で一括配布（update-project.sh --auto。`.codex-manifest` の3分類で案件カスタマイズは自動保護、CONFLICT は保持のうえレポート化）
4. CONFLICT が出た案件は `.kit-update-report-*.md` を見て手動マージ判断（カスタマイズが汎用的なら本体へ還流）
5. **CRITICAL（セキュリティ・重大バグ）は月次を待たず即配布**

互換性の考え方（何を壊してよいか）は `docs/operations/compatibility-contract.md` が正本。

## 還流すべきもの vs しないもの

### 還流すべき（本体に上げる）

- ✅ 複数案件で再利用できる知見
- ✅ どんな業界・規模でも当てはまる原則
- ✅ 新しいエージェントの必要性
- ✅ 既存エージェントの責務修正
- ✅ セキュリティ・コンプライアンス関連
- ✅ ベストプラクティス・アンチパターン
- ✅ 技術選定の判断材料

### 還流しない（案件側に留める）

- ❌ 案件固有のドメイン知識
- ❌ クライアント固有の要件・好み
- ❌ 特定の業界用語・規制
- ❌ 一度きりの設計判断

## 判断フローチャート

```
気付きがあった
    ↓
これは他の案件でも起こるか？
    ↓ Yes              ↓ No
    ↓              [案件のLEARNINGSに記録のみ]
他のフリーランスも遭遇するか？
    ↓ Yes              ↓ No
    ↓              [本体にプライベート反映]
本体に反映するべきだが
公開すべきか？  
    ↓                   ↓
（プライベートリポジトリ運用なので公開判断は不要）
本体に Issue 作成 → PR
```

## 還流時のチェックリスト

PR作成時に確認：

- [ ] 該当ファイルが特定されている
- [ ] 改善内容が「汎用的」と説明できる
- [ ] 元の案件名は出さない（プライバシー）
- [ ] CHANGELOG.md に追記
- [ ] 影響範囲（他エージェントへの波及）を確認
- [ ] バージョン番号を意識（major/minor/patch）

## バージョニング規則

セマンティックバージョニング：

| 変更レベル | バージョン | 例 |
|----------|---------|-----|
| **MAJOR** | x.0.0 | エージェント間の連携プロトコル変更、破壊的変更 |
| **MINOR** | 0.x.0 | 新エージェント追加、新Skill追加、後方互換ある拡張 |
| **PATCH** | 0.0.x | 既存エージェントの内容改善、誤字修正、アンチパターン追加 |

## 案件側で発見した「やばい話」の扱い

セキュリティ脆弱性や重大バグを発見した場合：

1. **即座に本体に反映**（月次を待たない）
2. CRITICAL タグで CHANGELOG に明記
3. すべての既存案件に通知（影響範囲を判定）
4. 影響案件は緊急パッチを取り込む

## 還流が滞ったときの対策

3案件運用していて、本体に1ヶ月以上 PR がない場合：

- 各案件の LEARNINGS.md を見て、書かれているか確認
- 書かれていないなら「気付きを書く習慣」が崩れている → 修正
- 書かれていて還流していないなら「月次レビュー」を確実に実施

## project-manager エージェントとの連携

`@project-manager` には四半期に1度のリマインダー機能を組み込んだ：

```
今四半期もお疲れさまでした。
PROJECT_LEARNINGS.md を確認しましたか？
本体に還流すべき項目は X件あります：
- ...
```

詳細：`.codex/agents/project-manager.md` の改訂が必要（v0.2.0 以降）

## メトリクス

還流の健全性を測る指標：

- 月あたりの本体PR数
- 月あたりの新 learning 件数（各案件合計）
- 案件 → 本体への変換率（learning に書かれたうち、本体に上がった％）
- 既存案件のバージョン追随率

`docs/operations/metrics.md` で月次トラッキング（オプション）

## アンチパターン

1. **「忙しいから後で」で書かない**：気付きの90%は消える
2. **3案件分まとめて書こうとする**：1案件分すら書けない
3. **完璧な PR を書こうとして手が止まる**：粗くてもまず Issue を作る
4. **本体に上げずに案件で完結**：本体が成長しない（最大の失敗）
5. **すべてを上げようとする**：ノイズで本体が肥大化、判断軸を守る
